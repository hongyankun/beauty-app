# 路线图（Roadmap）

按阶段推进，**不设定日期，不估算工期**。阶段之间可以有少量重叠，但前一阶段的"完成标准"未达成时，不应开始下一阶段的核心工作。

相关文档：[项目简介](./PROJECT_BRIEF.md) · [架构](./ARCHITECTURE.md) · [决策记录](./DECISIONS.md)

---

## Phase 0 工程初始化与基线

**目标**：建立可靠、可重复、可被多个开发会话共享的工程基线。

**主要交付物**
- Expo SDK 57 + Expo Router + TypeScript strict 工程
- ESLint（`eslint-config-expo` flat config）
- `.gitignore` 覆盖环境变量与敏感文件
- 项目文档：PROJECT_BRIEF、ARCHITECTURE、DECISIONS、ROADMAP
- CLAUDE.md 开发规则

**完成标准**
- `npm run lint` 通过
- `npx tsc --noEmit` 通过
- `npx expo-doctor` 全部检查通过
- iOS 模拟器可正常启动
- 文档齐备且相互引用正确

**暂不处理**：CI 流水线、测试框架、EAS 构建配置、应用标识符。

---

## Phase 1 移动端信息架构与静态页面

**目标**：把五个 MVP 模块的骨架搭出来，确定导航结构与页面层级，先解决"去哪里"，不解决"数据从哪来"。

**主要交付物**
- 首页、记录、医美百科、心愿单与收藏、我的 —— 五个入口的路由与布局
- 核心闭环涉及的页面占位：套餐列表、套餐详情、新增套餐、核销
- 基础视觉规范（颜色、间距、字号）落到 `constants`
- 清理 Expo 模板示例文件

**完成标准**
- 全部页面可通过导航到达，无死链
- 使用写死的示例数据渲染，不接任何持久化
- lint 与 tsc 通过

**暂不处理**：真实数据、持久化、表单校验、账号、动效打磨。

---

## Phase 2 核心数据模型与本地业务闭环

**目标**：跑通第一阶段核心闭环，数据先落本地，但结构按未来要同步到云端来设计。

**主要交付物**
- **（已完成）** `db` 层基础：expo-sqlite 依赖、版本化迁移机制、数据库 Provider 与启动时自动初始化（[ADR-013](./DECISIONS.md#adr-013-本地持久化使用-expo-sqlite)）
- **（已完成）** V1 表结构：profiles / institutions / purchases / purchase_items / redemption_records，含外键、约束与索引
- Purchase / PurchaseItem / Redemption 的领域模型与类型定义（当前只有数据库行类型）
- repository 实现 + 为同步预留的操作队列结构
- Institution 的新增与复用逻辑（表结构已就绪，业务逻辑未实现）（[ADR-014](./DECISIONS.md#adr-014-机构作为可复用的独立实体)）
- 剩余次数的派生计算逻辑（由购买数量与有效核销记录算出，不可直接改写）
- 套餐永久删除与核销作废的业务操作与确认 UI（规则已定，见 [ADR-016](./DECISIONS.md#adr-016-套餐永久删除核销记录使用作废机制)；表结构已就绪，业务逻辑与界面未实现）
- 完整闭环：新增套餐 → 添加项目 → 查看详情 → 核销 → 余次更新 → 首页统计更新

**完成标准**
- 闭环全流程可用，App 重启后数据不丢
- 金额全程以整数分处理，无浮点参与
- 余次在任何路径下都与核销记录一致，不存在可直接编辑余次的入口
- lint 与 tsc 通过

**暂不处理**：多设备同步、账号、云端存储、数据导出。

---

## Phase 3 后端、账号与云同步

**目标**：引入服务端，把权威数据源迁到云端，本地降级为缓存。

**主要交付物**
- NestJS + PostgreSQL + Prisma 后端服务
- REST API + OpenAPI 文档
- Account 与 Profile 分离的账号体系与认证（数据模型层分离；第一版仍只有一个个人档案，不开放切换与多人管理，见 [ADR-015](./DECISIONS.md#adr-015-第一版只做个人档案不做多人)）
- 基于操作队列的同步机制与冲突处理策略
- 本地已有数据向账号迁移的方案

**完成标准**
- 用户可注册登录，数据随账号在多设备间保持一致
- 离线操作可在恢复网络后正确回放
- 用户只能访问自己的数据，权限有服务端校验
- 无任何全量覆盖式同步逻辑

**暂不处理**：多人共享账户、B 端接口、数据分析后台。

---

## Phase 4 百科、收藏与心愿单

**目标**：补齐高频使用场景，让低频记录之外有持续打开的理由。

**主要交付物**
- 医美百科的内容结构、分类与检索
- 收藏功能
- 心愿单：想做的项目及其与百科条目的关联

**完成标准**
- 百科内容可浏览、可检索、可收藏
- 心愿单可增删，并能与记录模块建立关联
- 内容中立客观，不含疗效承诺，不含机构导流

**暂不处理**：社区、评论、UGC、机构评分、内容推荐算法。

---

## Phase 5 提醒、统计与 AI 辅助

**目标**：在已有数据之上提供价值增量，降低套餐遗忘和浪费。

**主要交付物**
- 待核销与套餐到期提醒
- 消费与使用情况统计
- AI 辅助：记录总结、待办提醒、一般性知识解释、面诊提问清单生成

**完成标准**
- 提醒准确，不误报不漏报
- 统计口径与记录数据完全一致
- AI 输出严格落在 [ADR-009](./DECISIONS.md#adr-009-ai-定位为记录与科普助手不是医生) 界定的范围内，具备越界拦截
- AI 相关的密钥不出现在客户端

**暂不处理**：复杂个性化推荐、基于用户画像的项目推荐。

---

## Phase 6 内测、安全和合规

**目标**：在面向真实用户前完成安全与合规检查。

**主要交付物**
- 隐私政策与用户协议
- 权限申请文案与最小化收集核查
- 敏感数据存储、传输与日志脱敏检查
- 内测渠道与问题收集机制

**完成标准**
- 无敏感信息硬编码，无密钥进入客户端包
- 日志不含完整敏感信息
- 实际收集的个人信息与隐私政策声明一致
- 内测反馈的阻塞级问题清零

**暂不处理**：大规模压测、多地域部署。

---

## Phase 7 应用商店发布

**目标**：完成上架所需的全部工程与材料准备。

**主要交付物**
- `ios.bundleIdentifier` / `android.package` / 正式应用名
- EAS 构建与提交配置、`runtimeVersion` 与更新策略
- 应用图标、启动图、商店截图与描述文案
- 版本号与发布流程

**完成标准**
- 生产构建可在真机稳定运行
- 通过目标应用商店审核
- 具备可回滚的发布流程

**暂不处理**：增长投放、ASO 优化、多语言。
