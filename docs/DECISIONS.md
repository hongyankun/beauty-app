# 决策记录（Architecture Decision Records）

本文件是项目的决策日志。**已记录的决策不得在单次任务中被随意推翻**——如果新需求与某条 ADR 冲突，停止执行并提出问题，由产品负责人决定是否新增一条 ADR 来覆盖它。

本文件只记录**已经确定**的决策。尚未决定的事项不写在这里，写在 [ROADMAP](./ROADMAP.md) 的待决策项中。

## ADR-001 使用 Expo 和 React Native 跨平台开发

- **状态**：Accepted
- **背景**：产品需要同时覆盖 iOS 和 Android 个人用户，开发资源有限，无法维护两套原生代码。
- **决策**：采用 React Native + Expo（SDK 57）作为移动端技术栈，走 CNG（持续原生生成）流程，不提交 `ios/`、`android/` 目录。
- **原因**：一套代码覆盖双端；Expo 提供开箱可用的构建、更新和原生模块生态；CNG 避免手工维护原生工程带来的漂移。
- **影响**：原生能力受 Expo 生态约束，需要自定义原生模块时须走 development build；升级 SDK 时依赖版本必须整体对齐，不可单独手改。

## ADR-002 TypeScript 作为主要语言并保持 strict

- **状态**：Accepted
- **背景**：业务涉及金额、次数、日期等易错数据，需要在编译期拦截错误。
- **决策**：全项目使用 TypeScript，`tsconfig.json` 保持 `strict: true`，不因个别报错而放宽。
- **原因**：strict 模式能捕获空值和类型不匹配，这类问题在余次计算和金额处理上代价极高。
- **影响**：每个任务完成后必须通过 `npx tsc --noEmit`；引入的第三方库应有类型定义；禁止用 `any` 绕过问题。

## ADR-003 移动端优先，Web 只作为辅助预览

- **状态**：Accepted
- **背景**：目标用户在手机上使用，但 Expo 模板同时提供 Web 支持。
- **决策**：所有设计与功能以 iOS/Android 为准，Web 仅作为开发期的辅助预览，不作为正式交付形态。
- **原因**：集中资源保证移动端体验；Web 端的 SSR/hydration 差异会显著增加成本。
- **影响**：`.web.tsx` / `.web.ts` 平台分支文件保留但不投入额外功能开发；Web 端出现问题时优先级低于移动端；不为 Web 单独做适配设计。

## ADR-004 从 0 重建，不复用原 beauty_tracker 代码

- **状态**：Accepted
- **背景**：此前存在一个早期项目 beauty_tracker，其数据模型与架构不满足当前目标（尤其是本地主数据 + 全量覆盖同步的做法）。
- **决策**：本项目从空白 Expo 工程重新开始，不迁移、不复制原有代码。
- **原因**：旧实现的架构缺陷会随代码一起被带入；重建的成本低于持续修正错误的地基。
- **影响**：不存在向后兼容负担；旧项目的产品经验可以参考，但代码和数据结构不得直接照搬。

## ADR-005 云端数据库最终作为权威数据源

- **状态**：Accepted
- **背景**：用户可能换机或多设备使用，医美记录是长期资产，丢失不可接受。
- **决策**：云端 PostgreSQL 为唯一权威数据源；手机本地仅作为缓存与离线操作队列；**禁止**本地主数据 + 全量覆盖同步。
- **原因**：全量覆盖同步在并发或多设备场景下会静默丢数据；以服务端为准 + 操作队列可以保证可恢复、可审计。
- **影响**：Phase 2 的本地实现必须预留同步字段与操作队列的位置，不能写成"只能本地用"的结构；Phase 3 接入后端时应尽量不改动 UI 层。

## ADR-006 金额使用整数分

- **状态**：Accepted
- **背景**：套餐金额需要参与累加、分摊与统计。
- **决策**：所有金额以"分"为单位、以整数存储和传输，禁止使用浮点数。展示时再格式化为元。
- **原因**：浮点运算存在精度误差，在累计统计中会逐步放大，金额出错会直接摧毁产品可信度。
- **影响**：数据模型、API 和本地存储中的金额字段统一为整数；输入与展示层负责元/分转换；任何金额相关计算不得引入 `float`。

## ADR-007 Account 与 Profile 分离

- **状态**：Accepted
- **背景**：账号身份（登录凭证）与用户资料（昵称、偏好等）的生命周期和敏感级别不同。
- **决策**：数据模型中 Account 与 Profile 拆为两个实体。
- **原因**：认证信息需要更严格的保护和更少的读写；资料信息频繁变更且可能扩展；分离后便于权限收敛与最小化收集。
- **影响**：Phase 3 设计后端表结构时按两张表实现；客户端不得把认证信息与资料混在同一份缓存里。

## ADR-008 第一版不做照片功能

- **状态**：Accepted
- **背景**：医美类产品常见"前后对比照"，但面部照片属于高度敏感的个人生物信息。
- **决策**：第一版不引入相机、相册、照片存储与前后对比功能。
- **原因**：显著降低隐私合规风险与上架审核难度；避免过早承担敏感数据的加密、传输和留存责任；核心价值（套餐资产管理）不依赖照片。
- **影响**：不申请相机/相册权限，`app.json` 中不添加相关隐私声明；任何任务都不得以"顺手加一下"的方式引入图片采集能力；若未来要做，需新增 ADR 并配套完整的隐私方案。

## ADR-009 AI 定位为记录与科普助手，不是医生

- **状态**：Accepted
- **背景**：医美涉及医疗属性，AI 输出若越界会带来法律与安全风险。
- **决策**：AI 能力严格限定为总结记录、提醒待核销、解释一般性知识、生成面诊提问清单；不得诊断、不得判断用户是否适合某项目、不得制定治疗方案、不得替代医生。
- **原因**：合规底线，同时也是用户信任的基础；错误的医疗建议可能造成实际伤害。
- **影响**：所有 AI 提示词、输出文案与 UI 说明都须体现该定位；涉及个体化医疗判断的请求应引导用户咨询有资质的医生；详见 [PROJECT_BRIEF 第 7 节](./PROJECT_BRIEF.md#7-产品边界ai-能力红线)。

## ADR-010 第一版先完成套餐与核销闭环

- **状态**：Accepted
- **背景**：MVP 规划了五个模块，同时推进会导致每个都做不完整。
- **决策**：第一阶段集中完成"新增套餐 → 添加项目 → 查看详情 → 核销 → 余次更新 → 首页统计"这条闭环，其余模块延后。
- **原因**：这条闭环是产品不可替代价值的最小载体；先验证它，再扩展高频的知识模块。
- **影响**：百科、心愿单、收藏、提醒等在闭环跑通前只做信息架构占位，不做功能实现；资源冲突时优先保障闭环。

## ADR-011 暂不引入状态管理和 UI 组件库，等待具体需求

- **状态**：Accepted
- **背景**：项目尚无业务代码，无法判断真实的状态复杂度和 UI 需求。
- **决策**：当前不引入任何状态管理库和第三方 UI 组件库，先用 React 内置能力和模板自带的主题组件推进。
- **原因**：过早选型会锁定架构；等真实痛点出现后再选，决策依据更充分；也能避免引入不必要的包体与升级负担。
- **影响**：Phase 1、Phase 2 用 React 内置状态推进；当出现明确的跨页面状态共享或复杂表单需求时，再新增 ADR 讨论选型。

## ADR-012 不在没有架构决策的情况下增加依赖

- **状态**：Accepted
- **背景**：依赖一旦进入项目就难以移除，且会影响 Expo SDK 升级路径。
- **决策**：任何新增运行时依赖都必须先有对应的 ADR 或明确授权；不得在实现任务中顺手安装。
- **原因**：控制包体和攻击面；保证依赖与 Expo SDK 版本矩阵兼容；避免不同会话各自引入功能重叠的库。
- **影响**：遇到需要新依赖的任务时应先停止并提出建议；Expo 相关依赖只能通过 `npx expo install` 安装以保证版本对齐；禁止执行 `npm audit fix --force`（会导致 Expo 大版本降级）。

## ADR-013 本地持久化使用 expo-sqlite

- **状态**：Accepted
- **背景**：Phase 2 需要把套餐与核销闭环落到本地，此前本地持久化方案一直是待决策项。核心业务数据涉及金额、次数与派生余次，要求可事务、可查询、可版本化演进。
- **决策**：第一阶段核心业务数据使用 **expo-sqlite**。具体约束：
  - 核心业务数据**不得**使用 AsyncStorage 或普通 JSON 文件作为主存储（轻量偏好设置除外）。
  - 第一阶段**不引入 ORM**，直接使用 expo-sqlite 提供的 API。
  - 页面**不得直接执行 SQL**；所有数据访问必须经过 repository / service 层。
  - 业务主键使用 **UUID 字符串**，不使用数据库自增 ID，为未来云同步预留。
  - 数据库必须采用**版本化迁移**，禁止通过删库或删表重建的方式升级。
  - 初始化时启用**外键约束**。
  - 初始化时启用 **WAL**。
  - 用户输入必须使用**参数化查询**，禁止字符串拼接 SQL。
  - 创建套餐及其套餐项目需要**事务保护**。
  - 核销、撤销核销及余次校验需要**事务保护**。
  - `remaining` 仍然是**派生结果**，由购买次数与有效核销记录算出，不单独保存。
- **原因**：SQLite 提供事务与关系约束，能保证"余次与核销记录始终一致"这一核心正确性要求；expo-sqlite 是 Expo 官方模块，版本矩阵与 SDK 对齐；不上 ORM 可以避免过早锁定抽象，也避免为一个尚无复杂查询的项目引入额外包体与升级负担。UUID 与版本化迁移是为 Phase 3 云同步预留的前提，见 [ADR-005](#adr-005-云端数据库最终作为权威数据源)。
- **影响**：Phase 2 实现时需先建立 `storage` 层的迁移机制与 repository 接口，再写业务；任何"先用 AsyncStorage 顶一下"的临时实现都视为违背本 ADR；若未来确需 ORM，须新增 ADR。**本 ADR 只记录目标架构，本轮不实施，也不安装依赖。**

## ADR-014 机构作为可复用的独立实体

- **状态**：Accepted
- **背景**：用户常在多家机构消费，机构名称会在购买与核销中反复出现。此前"机构标准化策略"为待决策项，存在"纯文本输入"与"依赖外部机构名录"两种方向。
- **决策**：使用 **Institution** 作为独立实体表示机构。具体约束：
  - **不依赖外部机构名录**作为第一阶段的前置条件。
  - 用户可以**自由新增**机构。
  - 已录入的机构**自动进入可复用列表**，供后续购买与核销直接选择。
  - 购买记录与核销记录通过 **`institutionId`** 关联机构。
  - 核销**默认继承套餐机构**，但允许用户选择另一个已有机构，或当场新增机构。
  - 机构名称必须做**基础清洗**，例如去除首尾空格。
  - 第一阶段**不要求**解决全国同名机构、品牌集团、门店认证等复杂问题。
  - "机构合并"作为后续能力，**不进入当前实现范围**。
- **原因**：独立实体让"我在哪几家店消费"成为可统计维度，而纯文本输入会因错字与空格产生大量伪机构；自动记忆复用显著降低重复录入成本，这是移动端单手操作的关键；不依赖外部名录可以避免第一阶段被数据源采购和维护阻塞。
- **影响**：数据模型需要 Institution 表与外键；录入表单的机构字段是"可搜索的选择器 + 新增"而非纯输入框；历史名称快照仍需保留，避免机构改名导致旧记录失真；同名机构在第一阶段允许并存，不做自动合并。

## ADR-015 第一版只做个人档案，不做多人

- **状态**：Accepted
- **背景**：原网页版支持多用户，并区分"购买人"与"消耗人"（如"妈妈买、女儿做"）。该能力被继承进了移动端 PRD 草案，导致第一版表单出现两个档案选择框、首页出现档案切换入口。经评估，这显著增加了第一版的录入成本与界面复杂度，而首批用户的主诉求是管理自己的套餐。
- **决策**：第一版**只做个人档案**。具体约束：
  - 第一版只有**当前用户本人一个档案**。
  - **不提供** Profile 切换入口。
  - **不提供**多人档案管理页面。
  - **不提供**"购买人""实际消耗人"选择框。
  - 所有购买、项目、核销、心愿与收藏**均属于当前用户**。
  - 当前版本的统计与筛选**不包含"消耗人"维度**。
  - 数据模型**可以保留** owner / account / profile 归属字段，为未来升级预留。
  - 多人档案只能通过**未来新的产品决策和 ADR** 引入。
- **原因**：录入摩擦是记录类产品的头号流失原因，每多一个必填选择框就多一次放弃机会；多人场景在首批用户中占比未经验证，不应以第一版的复杂度为其买单；保留归属字段可以让未来升级是"加入口"而不是"改数据模型"。
- **影响**：本 ADR **正式覆盖**旧 PRD 中"购买人与实际消耗人可以不同"的规则，相关字段、表单项、筛选维度与验收标准一并从第一版移除。[ADR-007](#adr-007-account-与-profile-分离) 依然有效——Account 与 Profile 在**数据模型层**仍然分离，本 ADR 限制的是**第一版的用户可见功能**，两者不冲突。未来若要开放多人，需新增 ADR 并同步更新 PRD 与信息架构。
- **后续取代范围**：本节记录本决策做出之后发生的事，不修改上面的决策与当时的表述。
  - **2026-09-23**，[ADR-022](#adr-022-使用人作为独立实体以外键--名称快照保存) 部分取代本 ADR，**自 schema v4 生效**：引入同一档案下的使用人实体，购买记录保存购买人、每条使用记录保存使用人，默认均为「自己」。
  - **仍然有效的部分**：一个 Account 仍只有一个 Profile；不提供 Profile 切换入口与多档案管理；使用人不是档案、不登录、不持有数据。
  - schema v4 上线之前，本 ADR 的全部约束继续适用于当前实现（schema v3）。

## ADR-016 套餐永久删除，核销记录使用作废机制

- **状态**：Accepted
- **背景**：首版数据库 schema 实施时，"删除与审计策略"（[ROADMAP](./ROADMAP.md) 待决策项 Q-10）尚未确定，`purchases` 表按软删除思路预留了 `deleted_at` 列。产品负责人评估后认为：回收站会让"我到底还有多少套餐"这个核心问题产生第二个答案，而这正是本产品要消除的困惑；同时第一版没有云端，软删除既无同步需求，也没有恢复入口去消费它。但"误点一次核销"与"删掉整个套餐"是两种完全不同的错误——前者高频且代价小，后者低频且用户会谨慎确认。
- **决策**：**两种删除走两条不同的路径**。
  - **套餐删除 = 二次确认后物理删除。**
    - 确认框必须显示将受影响的**项目数量与核销记录数量**，并明确告知**删除后不可恢复**。
    - 用户确认后执行真正的 `DELETE`，`purchase_items` 经外键级联删除，`redemption_records` 再经 `purchase_items` 级联删除。
    - **Institution 不随套餐删除**，其生命周期由归档（`is_archived`）管理；Profile 同样不受影响。
    - 删除后相关数据不再进入任何历史统计。
    - **不提供回收站，不提供恢复入口**，`purchases` 表**不保留** `deleted_at` 列。
  - **单次核销纠错 = 作废，不物理删除。**
    - 用户界面使用"撤销核销"等产品语言，不暴露 `void`。
    - 撤销后 `status` 改为 `void`，原记录保留，并写入 `voided_at` 与 `void_reason`。
    - 剩余次数只统计 `status = 'active'` 的记录，因此撤销后余次自动恢复。
    - 不提供删除单条核销记录的入口。
- **原因**：套餐是用户主动建立的顶层容器，删除它是一次明确的、带确认的决定，保留一份看不见的副本只会让统计口径与"用户以为的现状"分叉；核销则是高频快速操作，误点概率高，而它同时是余次的唯一依据，物理删除会让"这次到底做没做"永久失去证据，作废既恢复了余次又保住了审计线索。两者的差异不在于数据重要性，而在于**误操作的概率与可确认性**。
- **影响**：Q-10 由此关闭。首版 `purchases` 表不含 `deleted_at`，任何依赖软删除的查询条件都不成立；删除套餐的业务操作与确认 UI 属于后续任务，本轮只固化数据库结构。**未来接入云同步时，物理删除无法靠"比较两边的行"传播**，需要新增 ADR 设计删除同步或 tombstone 机制，**不得假设当前存在 `deleted_at` 可用**（与 [ADR-005](#adr-005-云端数据库最终作为权威数据源) 的操作队列同步方向一致）。核销的作废机制不受本 ADR 影响，继续保留。
- **后续取代范围**：本节记录本决策做出之后发生的事，不修改上面的决策与当时的表述。
  - **2026-09-23**，[ADR-021](#adr-021-删除套餐不再删除真实历史使用记录保留历史快照) 部分取代本 ADR，**自 schema v4 生效**：删除套餐时，其项目仍被永久删除，但引用这些项目的使用记录**不再级联删除**，而是改为「原套餐已删除」来源并保留全部快照。
  - **仍然有效的部分**：套餐删除仍是二次确认后的物理删除，不提供回收站与恢复入口，`purchases` 不加 `deleted_at`；单次使用的纠错仍只能作废、不能单条物理删除；机构与档案不随套餐删除。
  - schema v4 上线之前（即当前 schema v3），删除套餐仍按本 ADR 原文级联删除核销记录。

## ADR-017 套餐过期后仍允许核销，但保存前必须明确提醒

- **状态**：Accepted
- **背景**：套餐的有效期是机构与用户之间的约定，不是 App 能够单方面执行的规则。现实中机构常常在过期之后仍然同意用户把剩下的次数做完，也存在用户事后补录一次「其实发生在有效期之内」的核销。此前「过期后余次如何处理」是 [ROADMAP](./ROADMAP.md) 的待决策项，导致余次的派生口径存在两种互斥的可能：过期即清零，或过期完全不影响余次。这个口径不确定下来，核销就无法实现。
- **决策**：**过期不是硬性拦截，而是一次明确的提醒。**
  - **有效期不改变余次**：剩余次数始终是「购买次数 − 有效核销数」，套餐过期本身**不会**把剩余次数变成 0，也不会让项目失去核销入口。
  - 当一次核销的**核销日期晚于套餐有效期**时，保存前必须弹出二次确认，并在确认框中同时显示**套餐有效期**与**本次核销日期**。
  - 判断依据是**核销日期与有效期的比较**（`redeemedOn > expiresOn`），**不是**「今天是否已经过了有效期」。为一个今天已经过期的套餐补录一条发生在有效期之内的核销时，不提醒。
  - 提醒文案只陈述日期这一客观事实，**不得**把「已过期」描述成医疗风险，也不得给出任何治疗、效果或适合与否的判断（[ADR-009](#adr-009-ai-定位为记录与科普助手不是医生)）。
  - 用户确认继续后**照常保存**：该次核销计为已使用，剩余次数减 1，与未过期的核销没有任何区别。
  - 用户选择返回检查时**不写入数据库**，表单中已填写的内容全部保留。
  - 有效期为空仍然表示未知或长期有效，不参与该判断（PRD-PUR-007、E-10）。
  - **「临期提醒阈值」不属于本决策**，仍然是未决事项（PRD 第 20.1 节 Q-12），不得由实现任务自行选定。
- **原因**：把过期做成硬拦截，会让 App 给出一个与用户真实资产状况相反的答案——次数明明还在、机构也认，App 却说不能用，这正是本产品要消除的困惑，而不是制造的。反过来，完全不提醒又会让用户在不知情的情况下把一条自己都记不清是否被机构认可的记录存进台账。二次确认是这两者之间唯一诚实的位置：它陈述事实、把决定权交还用户，并且不替机构做承诺。用核销日期而不是当天日期做判断，是因为核销记录描述的是「那一天发生了什么」，用今天的时间去评判一件过去的事实会把补录变成误报。
- **影响**：[ROADMAP](./ROADMAP.md) 待决策项「套餐是否有有效期，过期后余次如何处理」由此关闭。余次的派生逻辑不因本 ADR 发生任何变化，`expires_on` 不参与任何余次计算；已有的 `remaining = quantity − activeRedemptionCount` 口径（[ADR-013](#adr-013-本地持久化使用-expo-sqlite)）继续成立。核销表单需要同时拿到套餐的有效期才能做这个判断。「临期」与「已过期」作为**列表筛选维度**的定义不在本 ADR 范围内，仍待后续任务与阈值决策一并确定。
- **后续落实**：本节记录本决策做出之后发生的事，不修改上面的决策与当时的表述。
  - **2026-09-18**，[PRD](./PRODUCT_REQUIREMENTS.md) V1.7 第 8.4 节已落实**应用内**的临期与过期提醒（首页提醒区与完整提醒页）。
  - 首版**应用内**提醒窗口固定为**未来 30 个自然日**，用户不可配置。
  - 提醒状态分为**已过期**、**今天到期**、**即将到期**三种；到期当天记为「今天到期」，不记为已过期。
  - 已过期但仍有剩余次数的套餐**继续允许核销**，这与本 ADR「有效期不改变余次」的决策一致，未作任何更改；核销日期晚于有效期时仍沿用本 ADR 规定的二次确认，未新增第二套规则。
  - **用户可配置的临期阈值、系统推送通知及其默认值仍属于后续决策**（PRD 第 20.1 节 Q-12、第 12 章），不因本次落实而关闭。

## ADR-018 编辑套餐时，项目能否删除以是否存在核销历史为界

- **状态**：Accepted
- **背景**：[ADR-016](#adr-016-套餐永久删除核销记录使用作废机制) 定下了两种粒度的删除口径——**整个套餐**可以二次确认后永久删除并级联，**单条核销**只能作废不能物理删除。中间还有一个粒度当时没有结论：**套餐项目**。编辑套餐时用户可能发现某一行是录错的，需要把它拿掉；但同一个入口也能拿掉一个已经做过几次的项目，而那样做会连带删掉它下面的核销记录——包括已经被撤销、本应作为纠错证据保留下来的那些。编辑套餐是一个高频、低戒备的操作，不能让它成为绕过 ADR-016 审计承诺的后门。同时「购买次数不得小于有效核销次数」（PRD 第 6.4 节、E-06、PRD-PUR-008）此前只写在产品规则里，没有说明它应该由哪一层保证，实现上容易退化成只有表单校验。
- **决策**：**项目的可删除性由「有没有核销历史」判定，与历史是否有效无关。**
  - **完全没有核销记录的项目可以删除**，删除前必须二次确认并说明不可恢复；保存成功后该项目从套餐中永久消失，不进回收站。
  - **只要该项目存在任何核销记录就不允许删除，`active` 与 `void` 一视同仁。** 已撤销的核销是用户的纠错痕迹，是历史的一部分，不能因为编辑套餐被顺手抹掉——这正是 ADR-016 保留 `voided_at` / `void_reason` 想守住的东西。此时向用户说明原因，并明确他仍然可以**修改**这个项目的名称、分类、次数、金额与备注。
  - **一个套餐至少保留一个项目**（PRD-PUR-003），最后一个项目不能删除。
  - **既有项目按 ID 原地 UPDATE**，不得用「先全部删除再重新插入」的方式实现编辑。后者会让主键漂移，`redemption_records.purchase_item_id` 随即失去指向，等于用一次编辑抹掉全部核销历史。
  - **「购买次数不得小于该项目有效核销次数」由两层共同保证**：表单层即时提示最小可填值，事务层在写入前重新读取真实核销数再判一次。表单层的数据可能已经过时——页面停留期间用户完全可能在另一条路径上核销了一次。
  - **上述限制全部由 service 层在事务内保证，不改动外键与数据库级联规则。** 数据库层的 `ON DELETE CASCADE` 保持原样：它服务于「删除整个套餐」这一被 ADR-016 明确允许的路径，不应为了拦住另一条路径而被改写。项目删除语句自带 `NOT EXISTS (SELECT 1 FROM redemption_records …)` 作为最后一道闸，命中行数不为 1 即整体回滚。
  - **不新增字段**：不加 `deleted_at`，不加 `remaining`，不加任何记录「本项目是否可删」的列。可删与否是从核销记录派生的事实，落库就会有第二份真相。
  - **编辑套餐的机构或城市，不得改写既有核销记录中的机构与城市快照。** 核销快照记录的是「那一次实际在哪里做的」，与套餐当前登记的机构是两件事（[ADR-014](#adr-014-机构作为可复用的独立实体)、PRD-INST-005）。
- **原因**：判定标准如果用「有没有**有效**核销」，那么用户只要先撤销再删除，就能在两步之内合法地抹掉一段历史，ADR-016 对单条核销的保护就形同虚设。用「有没有**任何**核销」作界，规则才是封闭的，而且这条界线对用户也讲得通：这个项目你做过，所以它进了你的档案。代价是「误增了一个项目、又误核销了一次」的用户无法把它删干净——但那种情况有代价更低的出口（撤销核销、改名、把次数改成实际次数），而丢失历史没有任何出口。次数校验放两层，是因为两层解决的是不同的问题：表单层负责让用户当场看懂为什么不行，事务层负责在并发和过期页面下守住数据一致性，任何一层单独存在都不够。
- **影响**：编辑套餐的实现必须能读到每个项目的两个计数——有效核销数与含作废的全部核销数；前者用于次数下限，后者用于可删性判定。保存必须在一个事务内完成「更新套餐 + 更新既有项目 + 插入新项目 + 删除已确认移除的项目」，并在事务内重新读取后做最终校验，任一步失败整体回滚。删除套餐（ADR-016）与撤销核销的既有语义不受本 ADR 影响。未来接入云同步时，项目删除与套餐删除一样属于物理删除，同样不能依赖「比较两边的行」来传播，需一并纳入 ADR-016 影响中所述的删除同步机制。

## ADR-019 从备份恢复采用「整体覆盖 + 单事务」，备份文件一律当作不可信输入

- **状态**：Accepted
- **背景**：[ADR-013](#adr-013-本地持久化使用-expo-sqlite) 把数据放在设备本地，没有账号也没有云端，用户换手机、误删 App 或送修之前唯一的退路就是自己导出的那份 JSON。备份导出已经落地（PRD 第 15.2 节），但只有导出没有恢复，那份文件对用户来说仍然只是一个存着、不知道能不能用的文件。实现恢复要先回答三个问题：恢复是覆盖还是合并；写入用什么事务边界；以及一个来自 App 之外、用户可以随意编辑、也可能来自别处的 JSON，应该被信任到什么程度。
- **决策**：
  - **恢复是对当前档案的整体覆盖，不是合并。** 库里有、备份里没有的数据会被删除，恢复完成后这台设备就是备份被导出时的那个样子。**不做合并、不做追加、不做选择性恢复**，不提供「只恢复心愿单」这类勾选。
  - **备份文件是不可信输入。** 扩展名与 MIME 只是选择器的提示，不作为信任依据；一律先做完整结构与不变量校验才可能进入写入。**绝不执行文件里的任何 SQL、表名或列名**，所有 INSERT 的列名都是代码里写死的字面量，值一律参数化绑定。多出来的字段会让校验失败，而不是被当作指令。
  - **`formatVersion` 与 `databaseSchemaVersion` 是两件事，都必须显式支持才接受。** 前者决定怎么解析，后者只用来判断这份备份是不是来自更新的数据库。**任何情况下都不因为文件里写着什么而修改 `PRAGMA user_version`**：备份不是 migration。来自更新版本的备份直接拒绝并说明，不做「尽量恢复」。
  - **校验全部发生在事务之外，写入全部发生在一个独占事务内。** 事务里按「子表在前」的顺序删除当前档案数据，再按依赖顺序写回，写完后在**同一个事务里**自查行数与六类孤儿引用，任何一条不过就抛出并整体回滚。失败后数据库逐行等于操作前，没有「删到一半」的中间态需要抢救。
  - **不关闭外键检查，也不依赖它。** `withExclusiveTransactionAsync` 跑在一条新连接上，`PRAGMA foreign_keys` 不继承，且 BEGIN 之后再开是静默无效的——它本来就没开，所以既不去关它，也不能指望它兜底。删除顺序、写入顺序与事务内自查共同承担这件事。
  - **业务记录的 ID、时间戳、null、整数分金额、`active` / `void` 状态与机构城市快照原样写回**，不重新生成 ID，不刷新 `updated_at`，不重算并持久化任何派生值。恢复**不调用**「新增套餐」「新增核销」这类正常写入 service：那些 service 的职责就是生成新 ID 与新时间戳，用它们恢复等于把历史改写成今天。
  - **单档案的 ID 归一集中在一个纯函数里**（`backup-profile-mapping.ts`），在解析阶段完成，之后全链路只认本机那个固定档案 ID。界面、hook 与 repository 都不做临时映射，恢复后也不允许出现第二个可用档案。
  - **覆盖前必须有摘要与二次确认两道明确的用户动作**，并且在摘要出现之前一行数据都不能写。用户取消选择文件或在确认框里选择返回检查，都是零改动的正常操作，不报错。
  - **文件体积上限固定为 10 MiB**，在 `JSON.parse` 与任何事务之前挡下；选择器给的体积不可信时，按读入文本的真实 UTF-8 字节数再量一次。
  - **导出与恢复共用同一个同步闸门**，在第一个 `await` 之前取得，不依赖异步 setState 作并发锁。
- **原因**：合并听起来更温和，实际上产生的是一个既不是现在、也不是备份时刻的第三种状态——重复的套餐、对不上的核销、说不清来历的机构，用户没有任何办法判断哪一份是真的。覆盖的语义只有一句话「让 App 回到导出那一刻」，用户按下按钮时期待的正是这个，代价是必须把「可能覆盖掉现在的数据」讲清楚，而这是二次确认能承担的。校验放在事务外，是因为一个持有独占锁的事务不该去做一堆与数据库无关的判断；写入放在一个事务内，是因为恢复中途失败留下半新半旧的库，比恢复失败本身严重得多——后者用户还能重试，前者连「现在这是什么」都答不上来。把备份当作不可信输入不是假想威胁：这个文件在用户的网盘和聊天记录里流转过，也可能被文本编辑器改过，而恢复是这个 App 里唯一一个由外部内容驱动的批量写入路径。
- **影响**：新增一个 `restore-repository.ts` 承担删除、写入与事务内自查，恢复相关的 SQL 全部集中在这里，screen、hook 与 route 中不出现 SQL 与 `expo-sqlite`。校验逻辑**复用并扩展导出侧已有的 validator**，不产生第二套会各自漂移的规则。新增 `expo-document-picker` 一个依赖用于调起系统文件选择器，不引入任何 JSON、ZIP 或数据库库。不新增迁移，不修改任何既有表结构。云同步（Phase 3）到来后，「整体覆盖」只适用于用户显式发起的本地恢复，不能作为同步策略复用——多设备之间的合并与冲突仍需按 [ADR-016](#adr-016-套餐永久删除核销记录使用作废机制) 影响中所述另行设计。备份加密、ZIP 打包、自动与定时备份、合并恢复与选择性恢复均**不在**本决策范围内，需新的 ADR 才可讨论。

## ADR-020 真实变美记录与套餐资产分离：BeautyEvent + UsageRecord，套餐只是可选来源

- **状态**：Accepted（2026-09-23，BT-0019D 冻结设计；随 schema v4 由 BT-0022 落地，当前实现仍为 schema v3）
- **背景**：当前模型里，一次「做了项目」只能以 `redemption_records` 的形式存在，而它的 `purchase_item_id` 是 `NOT NULL`——没有套餐就没有记录。现实中大量真实经历并不来自用户自己的套餐：单次付费、朋友请客、用了别人的卡、活动体验、几年前的补录、记不清来源。这些经历今天要么进不来，要么只能伪造一个套餐去装它。另一方面，「一次到店」常常包含几个项目、甚至几个人，而一条核销只能描述一个项目的一次使用。本产品的留存根基是「真实、连续的个人历史」（PRD 第 2.4 节），数据模型必须让真实记录先于资产存在。
- **决策**：
  - **真实记录分两层**：BeautyEvent 记录「哪天、在哪家机构、在哪个城市发生了一次变美」；其下 N 条 UsageRecord 各记录「一次项目使用」——做的是什么、谁做的、从哪里扣的次数。每条 UsageRecord 可以有不同的项目、来源、使用人与作废状态。
  - **套餐只是 UsageRecord 可选的来源**，由 `source_kind` 表达：`package_item`、`single_purchase`、`external`、`unlinked`、`deleted_package`。前两种必须关联 PurchaseItem，后三种必须不关联。Purchase 与 BeautyEvent 之间没有强制关联。
  - **一行 = 一次使用**，UsageRecord 没有数量列；作废只发生在 UsageRecord 这一层，剩余次数 = 购买次数 − 有效 UsageRecord 数，仍然派生、不落库。
  - **`redemption_records` 退役**：v3 → v4 迁移中每条旧核销逐行变为一个 BeautyEvent 加一条 `package_item` 来源的 UsageRecord，两者 ID 都复用旧核销 ID，状态、作废时间与原因、备注、创建与更新时间原样复制；**不合并**同一天同一机构的多条旧核销；迁移后删除旧表，不做双写。
  - **已保存的使用记录可以修正来源，但只限有效记录**：修正在一个独占事务内完成，关联到新的购买项目时在事务内重新校验同一档案、项目仍存在、余次 > 0、[ADR-017](#adr-017-套餐过期后仍允许核销但保存前必须明确提醒) 的过期确认以及不出现负余次；原来源的余次因派生计算自然恢复；改为 `external` 或 `unlinked` 时释放次数，已有的历史快照保持不变。**已作废的记录不能修改来源**，用户应新建一条记录。`deleted_package` 可以重新关联到一个有效的购买项目，成为 `package_item` 或 `single_purchase`（由目标购买的类型决定）。不改动表结构，完整步骤见 [DATA_MODEL_V4.md](./DATA_MODEL_V4.md) 第 5.5 节。
  - **修正来源不改变实际做的项目**：目标购买项目必须与这条记录的项目快照兼容——标准项目要求 `service_code` 完全相同；自定义项目要求 `category_code` 相同且自定义名称经项目统一归一化后完全相同；不按显示名称相似度、别名或任何模糊规则匹配，标准项目与自定义项目永不互相关联。界面可以只列出兼容且有余次的项目，但 service 在事务内独立重新校验；没有兼容且有余次的项目时只能改为 `external` 或 `unlinked`。兼容关联后只更新来源快照（套餐名称、套餐项目名称），项目快照（分类、目录代码、目录名称、自定义名称）不变。记错了项目不属于来源修正：作废记录仍不可编辑，有效记录是否支持「修改实际项目」由 BT-0023 单独设计，不得借来源修正绕过。
  - **BeautyPlan（未来打算）不属于本模型**：v4 不为它建表或占位；心愿单的 `planned_on` 也不是 BeautyPlan。
  - 完整的表结构、约束与迁移步骤以 [DATA_MODEL_V4.md](./DATA_MODEL_V4.md) 为唯一规范来源。
- **原因**：
  - **为什么不直接把 `redemption_records.purchase_item_id` 改成可空**：那样「核销」这个词就同时承载「从资产里扣一次」和「发生了一件事」两个含义，一张表上一半行有资产、一半没有，余次、统计与删除规则都要到处判断「这行是不是真的核销」；而且它依然是一行一个项目，装不下「一次到店做了三个项目」。
  - **为什么不在 `redemption_records` 上继续加列**：日期、机构与地点属于「那一次到店」，放在每个项目行上就会在同一次到店的几行之间重复、并且可以各自被改得互相矛盾。
  - **为什么是两层**：事件层回答「那天发生了什么」，只需要写一次；使用层回答「每个项目从哪来、给谁做」，才能让一次到店里的几个项目各有来源、各自作废。
  - 把来源做成显式枚举而不是「有没有 `purchase_item_id`」，可以让「外部来源」「暂不关联」「原套餐已删除」这三种没有资产的情况在界面和统计上被区分和如实描述。
- **影响**：v4 新增 `beauty_events`、`usage_records`，删除 `redemption_records`。余次、首页、临期提醒、记录详情与备份都改为读取 `usage_records`，口径不变。「记录一次变美」成为新的核心录入流程（BT-0023），来源修正按上文规则由 BT-0023 实现、不再另行决定；v4 上线前现有「快速核销」流程保持不变。备份格式随之升级到 v2（[ADR-019](#adr-019-从备份恢复采用整体覆盖--单事务备份文件一律当作不可信输入) 的覆盖与单事务原则不变）。

## ADR-021 删除套餐不再删除真实历史，使用记录保留历史快照

- **状态**：Accepted（2026-09-23，BT-0019D 冻结设计；**自 schema v4 生效**，部分取代 [ADR-016](#adr-016-套餐永久删除核销记录使用作废机制)）
- **背景**：ADR-016 规定删除套餐时项目与核销记录一并级联删除。在「核销只是资产的附属」的旧模型里这说得通；但 [ADR-020](#adr-020-真实变美记录与套餐资产分离beautyevent--usagerecord套餐只是可选来源) 把真实经历提升为独立事实之后，「我不想再看到这张卡」就不应该连带抹掉「我那天确实去做过」。用户删除套餐的常见理由（录错了、卡已转让、不想再管理）没有一个意味着那些经历没有发生。
- **决策**：
  - 删除套餐仍是**二次确认后的永久删除**，不提供回收站与恢复入口，项目随之删除。
  - 在**同一个事务**里，先把引用该套餐任一项目的全部 UsageRecord（有效与已作废一视同仁）改为 `source_kind = 'deleted_package'` 并清空 `purchase_item_id`，再删除项目与套餐。BeautyEvent 与 UsageRecord 一条都不删。
  - **`deleted_package` 的含义**：这次使用当时来自用户自己的某个套餐，但那个套餐已被用户删除。它不占用任何余次，只能由删除套餐产生，新建时不可选择，修正来源时也不能作为目标；但有效的 `deleted_package` 记录可以重新关联到一个有效的购买项目（[ADR-020](#adr-020-真实变美记录与套餐资产分离beautyevent--usagerecord套餐只是可选来源) 的来源修正规则），或改为 `external` / `unlinked`。
  - **UsageRecord 始终保留历史快照**：使用人名称、项目分类与项目名称、来源套餐名称与套餐项目名称。套餐被删除后，这些快照就是「当时用的是哪张卡的哪个项目」唯一的线索，因此写入后永不因套餐、项目、人或目录改名而回写；唯一例外是用户主动把一条有效记录重新关联到另一个购买项目时，来源套餐与套餐项目名称快照随之改为新目标的名称（改为外部来源或暂不关联时快照保持不变）。
  - **BeautyEvent 由用户单独删除**：二次确认并显示将一并删除的使用记录数；删除事件会删除其下全部使用记录（这是整条记录的清除，不是单条使用的纠错路径），被释放的有效次数回到对应套餐。
  - **schema v3 保持旧行为**：v4 上线之前，删除套餐仍按 ADR-016 原文级联删除核销记录，不提前改变当前实现。
- **原因**：资产与经历是两个事实，删除一个不应顺带销毁另一个。保留快照而不是保留一个「已删除的套餐」影子行，是为了不让回收站以另一种形式回来——ADR-016 拒绝回收站的理由（「我到底还有多少套餐」不能有第二个答案）依然成立：删除后资产视图里确实没有这张卡了，只是历史视图里仍能看到那天做过什么、当时记在哪张卡上。
- **影响**：删除套餐的确认文案要从「核销记录将一并删除」改为「相关的变美记录会保留，只是不再关联这个套餐」。统计中，已删除套餐的使用记录不计入任何资产统计，但计入历史与次数类统计。`usage_records.purchase_item_id` 使用 `ON DELETE RESTRICT` 作为最后一道保护。云同步的删除传播问题（ADR-016 影响）不因本 ADR 改变。

## ADR-022 使用人作为独立实体，以外键 + 名称快照保存

- **状态**：Accepted（2026-09-23，BT-0019D 冻结设计；**自 schema v4 生效**，部分取代 [ADR-015](#adr-015-第一版只做个人档案不做多人)）
- **背景**：ADR-015 为降低第一版录入成本，去掉了「购买人」与「实际消耗人」。但真实记录模型（ADR-020）必须能表达「这张卡是我买的、我妈在用」和「今天我和朋友一起做了项目」——否则用户要么不记，要么把别人的使用记在自己名下，余次与历史都会失真。同时，ADR-015 反对的是**多档案**（切换入口、多套数据、首屏复杂度），而不是「一次使用是谁做的」这个事实本身。
- **决策**：
  - 新增 `people` 表，表示**同一档案下**被记录的人。不叫 `users`：这些人不登录、不持有凭证、不拥有数据，与 Account 无关（[ADR-007](#adr-007-account-与-profile-分离) 不变）。
  - **购买人记在 Purchase 上，使用人记在每条 UsageRecord 上**；BeautyEvent 不带人字段。两者都必填，默认「自己」，均以「外键 + 名称快照」保存：外键用于筛选和聚合，快照保证改名后历史不变。
  - 每个档案**恰好一个**「自己」（`is_self = 1`），由 v4 迁移创建，使用固定 ID；代码查找「自己」一律按 `is_self`，不按常量。「自己」不可归档、不可删除，v4 范围内不可改名。
  - 其他人可以归档：历史中照常显示，新建记录时隐藏。**被任何记录引用的人不能物理删除。** 人名按归一化名称在档案内判重，service 在事务内检查，唯一索引兜底。
  - **不收集敏感个人信息**：不设手机号、身份证号、生日、性别、关系或健康字段。
- **原因**：人是「一次使用」的属性，不是档案；把它做成档案会把 ADR-015 已经拒绝过的复杂度带回来，把它做成自由文本则会让同一个人因为错别字变成几个人、无法筛选。外键 + 快照是机构（[ADR-014](#adr-014-机构作为可复用的独立实体)）已经验证过的做法。默认「自己」让不关心多人的用户录入成本不变。
- **影响**：ADR-015 中「不提供购买人、实际消耗人选择框」「统计与筛选不含消耗人维度」两条自 v4 起不再适用；「一个 Account 一个 Profile、无档案切换、无多档案管理」继续有效。使用人管理入口由 BT-0020 交付，在「我的」下；删除与改名交互以 [DATA_MODEL_V4.md](./DATA_MODEL_V4.md) 第 4.2 节为准。

## ADR-023 `allocated_amount_minor` 是套餐项目金额的唯一事实

- **状态**：Accepted（2026-09-23，BT-0019D 冻结设计；随 schema v4 由 BT-0022 落地）
- **背景**：当前 `purchase_items.unit_amount_minor` 保存「单次分摊金额」，项目分摊总额由 单次 × 次数 派生，且允许与套餐总价不同（PRD-PUR-005）。用户在机构拿到的通常是「这张卡一共多少钱、里面几个项目各算多少」，而不是精确到分的单次价；3 次 1000 元这种组合，单次金额根本无法用整数分表达，只能让合计与总价差出几分钱。
- **决策**：
  - 每个 PurchaseItem 只保存**分配到该项目的总金额** `allocated_amount_minor`（整数分，≥ 0），`unit_amount_minor` 在 v4 中移除。**不同时保存两者**。
  - 赠送项目的分配金额可以为 0。
  - **最终保存时**，同一购买下各项目分配金额之和必须等于套餐总价：编辑过程中允许部分分配；超出总价阻止保存；不足时阻止最终保存并提示待分配金额。
  - 单次均价 = 分配金额 ÷ 次数，**只用于展示**，不能整除时标注「约」，永不回写。
  - **迁移规则**：`allocated = unit_amount_minor × quantity`，原样写入、不做调整；历史上与总价不一致的套餐保留原值，以派生判断标注「金额分配与总价不一致」，相关统计标注为估算值。
  - **历史不平衡套餐的保存规则**：新建套餐必须平衡；已经平衡的套餐保存后必须仍然平衡；历史不平衡的套餐在项目 ID 集合、项目数量、各项目购买次数、各项目分配金额与总价全部不变的前提下，只修改套餐名称、购买日期、有效期、机构、购买人、套餐备注、项目名称、项目分类、项目备注这九项元数据时，允许保留原差额，且修改项目名称、分类与备注不回写既有使用记录的快照；一旦修改总价、项目购买次数、项目分配金额，或新增、删除项目，保存前必须补平。界面显示差额，**永不自动修改金额**。这一区分由 service 层在保存事务内对比库中现值与提交值独立判断，不依赖界面。
- **原因**：保存单次金额会把一个经常除不尽的数当成事实，误差只能靠「允许不一致」来掩盖；保存分配总额则每一分钱都有归属，合计能严格等于总价，单次均价作为派生展示时出现的「约」是诚实的。两者同时保存等于有两份真相，一旦不一致就无法判断以谁为准（与 [ADR-006](#adr-006-金额使用整数分) 的整数分原则同源）。
- **影响**：PRD-PUR-005（差额超过 1 元提示但允许保存）自 v4 起由「最终保存必须平衡」取代；v4 之前继续有效。套餐表单改为两步式并加入金额分配（BT-0019C）。按使用日期统计的消耗金额改为按单次均价估算并标注。

## ADR-024 行政区与项目分类使用随 App 打包的版本化静态目录

- **状态**：Accepted（2026-09-23，BT-0019D 冻结设计；目录数据分别由 BT-0019B1 与 BT-0021A 交付）
- **背景**：城市目前是自由文本，「深圳」「深圳市」「shenzhen」会被当作三个地方；项目名称也是自由文本，同一个项目无法跨套餐归并查看。需要结构化，但产品没有服务端（ADR-013），也不能为了一个选择器引入网络依赖或把大量参考数据塞进用户数据库。
- **决策**：
  - 行政区（省、市两级）与项目分类（一级分类、二级项目）都是**随 App 打包的 TypeScript 静态数据**，带版本日期；**运行时不访问网络**，不在用户数据库中建表，**不进入备份**。
  - **稳定代码与显示名称分离**：数据库只保存代码与当时的名称快照；代码永不复用，改名只改显示名；停用条目仍能在历史中显示。现有七个项目分类取值原样保留为一级分类代码。
  - **回退**：历史记录始终展示快照；遇到当前目录不认识的代码时显示快照名称，不改写数据。目录找不到时，行政区可选「其他地区 / 暂未收录」，项目可以自定义；自定义项目永不自动聚合。旧数据只通过显式映射表迁移，不做模糊匹配。
  - **结构化地点只落在机构上**：`institutions` 新增 `province_code`、`province_name`、`city_code` 三列，`city` 继续作为显示名称、旧数据原文与「其他地区」的文字兜底。合法组合只有三种：三个代码全空（旧数据或「其他地区」）；省代码与省名称有值、市代码为空、`city` 为城市文字；三者齐全、`city` 为标准城市名称。任一代码有值时 `city` 不得为空，数据库 CHECK、备份校验与 service 三处同时拒绝其他组合（详见 [DATA_MODEL_V4.md](./DATA_MODEL_V4.md) 第 4.7 节）。旧机构只经显式、精确、唯一的映射补代码，对不上则保留 `city`、代码为空；「其他地区」允许代码为空并保存用户文字。创建 BeautyEvent 时把所选机构的省代码、省名称、市代码与 `city` 复制为事件快照；机构之后改名、改地点或归档都不回写快照。Purchase 只通过 `institution_id` 引用机构，不另存一套地点代码。备份 v2 的机构行包含三列，恢复校验代码与名称组合完整。
  - 项目目录**不等于**百科，也不构成医疗建议或覆盖承诺。
  - **数据来源与许可**留给 BT-0019B1 与 BT-0021A 确定，本 ADR 不指定。
- **原因**：静态目录离线可用、与 App 同版本发布、可审阅；不入库避免了「目录更新要不要迁移用户数据」的问题；不入备份是因为目录属于 App 而不属于用户，备份只需要代码与快照就能完整还原用户看到的内容。代码与名称分离使改名不会让历史失真。
- **影响**：数据库中的代码列不写枚举 CHECK，存在性由 service 在写入时校验；备份 validator 只校验代码非空。行政区与项目目录的选择器组件先于 schema v4 交付（BT-0019B1、BT-0021A），在 v4 之后才接线到表单（BT-0019B2、BT-0021B）。BT-0019B2 负责在新增与编辑机构时写入标准地点，并让新建与编辑套餐复用所选机构的地点，而不是在套餐表单里单独选择城市。
