## 2 产品概述

### 2.1 产品定义

一款面向个人消费者的**轻医美记录、套餐资产管理与中立科普 App**。它帮助用户记录买过和做过的轻医美项目，管理套餐剩余次数，并通过百科、收藏和心愿单持续了解项目、仪器与材料。

它不是交易平台，不是社区，也不是诊断工具。它的本质是"用户自己的医美消费与知识档案"。

### 2.2 用户痛点

用户在多家机构购买多个套餐后，常常难以回答：

- 在哪里买了什么套餐，花了多少钱。
- 每个项目买了几次、做了几次、还剩几次。
- 最近一次什么时候做，实际在哪家机构完成。
- 哪些套餐快到期，哪些项目长期没有使用。
- 某个项目、仪器或材料的基本原理、常见风险和一般性恢复信息是什么。
- 哪些项目正在关注，未来想做什么，心理预算是多少。

### 2.3 核心价值

- 管理医美套餐与剩余次数，降低遗忘、重复购买和套餐浪费。
- 保存真实、连续的个人医美消费历史，形成长期资产台账。
- 用中立百科、收藏和心愿单支撑长期使用。
- 基于用户自己的记录提供信息整理与一般性科普提示。

### 2.4 "记录低频、知识关注高频"的产品逻辑

医美**实际发生频率不高**（多数用户每月至多一两次），但用户对项目、仪器、材料和护理知识的**关注是高频的**。

由此得出关键设计约束：

- 记录模块决定产品的**不可替代性**，是留存的根，必须精确、可信、零数据丢失。
- 百科、收藏与心愿单决定产品的**打开率**，是活跃的来源。
- 产品不能只靠"记账"维持打开率，也不能用高频内容稀释记录的准确性。
- 产品不以促成交易为目标，不以机构广告替代中立信息，不通过制造焦虑促进消费。

## 3 目标用户与使用场景

### 3.1 目标用户

- 主要为 25 至 45 岁、有轻医美消费习惯的个人用户。
- 年度消费通常为数千元至数万元，可能同时在多家机构持有多张次卡或组合套餐。
- 关注光电、清洁、化学焕肤、注射、中胚层微针等项目。
- 愿意在购买后录入一次，并在每次完成项目后核销。

年龄与消费金额仅用于描述首批用户，**不构成注册限制**，界面不得据此筛选或标记用户。

### 3.2 核心使用场景

| 编号 | 场景 | 描述 |
| --- | --- | --- |
| S1 | 购买后录入 | 在机构购买套餐后，录入套餐名称、机构、城市、购买日期、总金额、有效期与包含的项目 |
| S2 | 完成后快速核销 | 完成一次项目后，在套餐项目上核销，确认日期、机构与城市，系统更新剩余次数 |
| S3 | 查看余次和有效期 | 随时查看每个项目还剩几次、哪些套餐临期、哪些已过期 |
| S4 | 回顾消费与项目历史 | 查看总消费、已核销金额、待核销金额、机构分布与项目时间线 |
| S5 | 查询项目、仪器、材料知识 | 搜索并阅读百科条目，了解原理、常见过程、恢复期与风险 |
| S6 | 收藏和记录想做项目 | 收藏百科内容，把想做的项目加入心愿单并记录预算与计划时间 |
| S7 | 换机与恢复 | 登录同一账号后恢复云端数据，并可导出自己的结构化记录 |

## 4 产品范围

### 4.1 V1 范围（首个公开测试版）

- 账号与个人档案（第一版只有当前用户本人一个档案）。
- 机构的新增、记忆与复用，以及机构管理（编辑、归档与恢复）。
- 套餐、套餐项目与核销记录的完整闭环。
- 剩余次数、有效期与基础提醒。
- 首页概览与基础消费统计。
- 百科浏览、搜索与收藏。
- 心愿单。
- 数据导出、账号注销与隐私入口。
- 基础离线查看与失败重试能力。

### 4.2 后续版本范围

- AI 辅助（总结记录、待核销整理、一般性知识解释、面诊提问清单）。
- Excel 导入导出增强。
- 更细的统计维度与图表下钻。
- 更丰富的提醒策略。
- 百科内容审核流与版本管理的产品化。
- 变美记录、使用人、金额分配、结构化地点与项目两级目录（schema v4，第 5B 章，已批准、尚未实现）。
- 变美计划（BeautyPlan），在 v4 之后以独立任务与独立迁移引入。

上述内容不作为 V1 的上线阻塞条件。

### 4.3 明确不做

以下为**已排除项**，不是"以后再说"。若要重新讨论，需新增一条 ADR（见 [PROJECT_BRIEF 第 6 节](./PROJECT_BRIEF.md#6-明确不做)）。

- 前后照片对比、皮肤照片上传、相机与相册权限（[ADR-008](./DECISIONS.md#adr-008-第一版不做照片功能)）。
- AI 皮肤诊断、治疗方案、效果预测或适合度判断（[ADR-009](./DECISIONS.md#adr-009-ai-定位为记录与科普助手不是医生)）。
- 社区、帖子、评论与私信。
- 机构评分、榜单与避雷曝光。
- 预约、交易、支付与团购。
- 机构入驻与机构后台。
- **B 端定价分析与数据产品**（任何版本均不在本 PRD 范围内，需新增 ADR 才可讨论）。
- 广告推荐与付费排名。
- 多人实时共享同一账号。
- 护肤品每日使用打卡。
- 复杂的个性化 AI 推荐。

### 4.4 医美范围边界

官方百科第一阶段**聚焦非手术轻医美**。记录模块允许用户自定义历史项目（包括手术类），但产品不主动提供手术项目的推荐、周期建议或效果承诺。

## 5 用户与档案

### 5.1 概念区分

| 概念 | 定义 | 说明 |
| --- | --- | --- |
| Account | 登录账号，数据所有权主体 | 认证凭证的归属 |
| Profile | 消费档案 | 不持有登录凭证。**第一版只有当前用户本人一个 Profile**，注册后自动创建，用户无需感知 |

**第一版不存在"购买人"与"实际消耗人"两个概念**：所有购买、项目、核销、心愿与收藏均属于当前用户本人（[ADR-015](./DECISIONS.md#adr-015-第一版只做个人档案不做多人)）。

> **v4 目标（已批准，尚未实现）**：schema v4 起引入同一档案下的**使用人**，购买记录保存购买人、每条使用记录保存使用人，默认均为「自己」（[ADR-022](./DECISIONS.md#adr-022-使用人作为独立实体以外键--名称快照保存)，第 5B.5 节）。「一个 Account 一个 Profile、不提供档案切换与多档案管理」不变。下面第 5.2 节中关于购买人、消耗人与消耗人维度的条款在 v4 上线前继续有效。

### 5.2 规则

- **数据模型必须区分 Account 与 Profile**（[ADR-007](./DECISIONS.md#adr-007-account-与-profile-分离)）。该分离只体现在数据模型层，不体现为第一版的用户可见功能。
- 第一版**只有当前用户本人一个档案**：不提供档案切换入口，不提供多人档案管理页面，不提供"购买人""实际消耗人"选择框。
- 第一版的统计与筛选**不包含"消耗人"维度**。
- 数据模型**可以保留** owner / account / profile 归属字段，为未来升级预留，但本阶段不得实现任何多人功能。
- 多人档案只能通过**未来新的产品决策和 ADR** 引入，不属于第一版范围。本规则正式覆盖原网页版 PRD 中"购买人与实际消耗人可以不同"的规则。
- 数据归属以 Account 为准；任何查询都必须按 Account 隔离，不得仅依赖客户端传入的标识。

## 5A 机构

### 5A.1 机构（Institution）字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| id | 是 | UUID |
| name | 是 | 机构名称，保存前去除首尾空格 |
| city | 否 | 所在城市 |
| notes | 否 | 备注 |
| createdAt / updatedAt | 是 | UTC ISO 时间戳 |
| isArchived | 是 | 是否已归档。已归档的机构不再出现在新增套餐与新增核销的机构选择列表，已有记录不受影响。见第 5A.3 节 |

### 5A.2 规则

机构是**独立可复用实体**（[ADR-014](./DECISIONS.md#adr-014-机构作为可复用的独立实体)）：

- 用户可以在录入购买或核销时**自由新增**机构，不依赖任何外部机构名录。
- 新增后的机构**自动进入可复用列表**，供后续购买与核销直接选择。
- 购买记录与核销记录通过 `institutionId` 关联机构。
- 机构字段的交互形态是**可搜索的选择器 + 当场新增**，不是纯文本输入框。
- 机构名称保存前必须做基础清洗，至少去除首尾空格。
- 核销**默认继承套餐的机构**，但允许改为另一个已有机构，或当场新增机构。
- 购买与核销同时保留录入当时的机构名称与城市快照，避免机构改名导致旧记录失真。
- 第一版**不解决**全国同名机构、品牌集团与门店认证问题；同名机构允许并存，不自动合并。
- **机构合并**属于后续能力，不在第一版范围内。

### 5A.3 机构管理（编辑、归档与恢复）

机构管理是"我的"Tab 下的一个整理入口，用于维护已经存在的机构主数据。它**不是**新的录入入口。

#### 5A.3.1 范围

- 入口位于"我的"的"数据管理"区块，页面见 [INFORMATION_ARCHITECTURE 第 3.5.2、3.5.3 节](./INFORMATION_ARCHITECTURE.md)。
- 列表分"使用中"与"已归档"两个筛选，默认"使用中"。
- 每个机构展示名称、当前状态、关联套餐数与关联核销数；城市与备注为空时整段省略。
- 关联条数按 `institutionId` 统计，**不得依据机构名称快照反推归属**。关联核销数**同时包含有效与已撤销**的核销记录。被永久删除的套餐及其级联删除的核销不再计入。
- **没有"新增机构"入口**：机构仍然只在新增套餐、编辑套餐与新增核销时创建或复用（第 5A.2 节）。
- **不提供删除机构**，不提供机构合并，不提供批量改名。

#### 5A.3.2 编辑

- 可编辑字段为名称（必填）、城市（选填）、备注（选填）。
- 名称去除首尾空格后不得为空；保存前按既有归一化规则判重，大小写、首尾空格、词间多余空格与全角空格不得绕过判重。
- 同一档案内不得再出现第二个归一化同名机构，判重**同时覆盖使用中与已归档**的机构。
- 冲突时给出中文业务说明并整体放弃保存，不向用户暴露数据库约束、表名或 SQL。
- 只修改城市或备注、或改名后归一化结果不变时，不因数据库中可能已存在的历史同名机构而阻止保存。
- 机构标识在编辑前后保持不变，既有套餐与核销记录的关联不会断开。

#### 5A.3.3 快照不回写

- **修改机构名称不改写**既有购买记录与核销记录的机构名称快照；**修改城市不改写**既有记录的城市快照。
- 机构管理页展示机构当前的主数据，历史记录展示各自当时的快照（PRD-INST-005、PRD-PUR-018）。
- **不提供"同步更新历史记录"操作**，任何场景下都不得用当前名称覆盖历史展示。
- 编辑页必须向用户说明这一点。

#### 5A.3.4 归档

- 使用中的机构可以归档，即使它仍被套餐或核销记录引用。
- 归档前二次确认，确认框显示机构名称、关联套餐数、关联核销数，并说明归档**不会删除**任何套餐与核销记录。
- 归档后该机构不再出现在新增套餐与新增核销的机构选择列表中。
- 归档**不是删除**：已有套餐、项目、核销记录及其快照全部保留，剩余次数、累计投入与各项统计不发生任何变化。

#### 5A.3.5 恢复

- 已归档的机构可以恢复，恢复后重新出现在机构选择列表中。
- 机构标识、创建时间与既有记录的关联在归档与恢复前后均保持不变。
- 恢复前需再次判重：若同一档案内已有一个**使用中**的归一化同名机构，则阻止恢复并给出中文说明，提示可先为其中一个改名。
- 恢复不会创建新机构。

#### 5A.3.6 再次使用已归档的机构名称

- 在新增套餐或新增核销中填入的机构名称，若归一化后与某个已归档机构一致，系统**复用原机构并自动恢复它**，不得新建第二个同名机构。
- 自动恢复与该次购买或核销的保存处于同一事务，保存失败时一并回滚。
- 自动恢复同样不改写任何历史快照。

## 5B 变美记录与套餐资产（v4 目标，已批准，尚未实现）

> **状态**：本章是 BT-0019D 冻结的**目标行为**，对应 schema v4 与备份 `formatVersion` 2，**当前一条都没有实现**。表结构、约束、迁移与备份格式的规范来源是 [DATA_MODEL_V4.md](./DATA_MODEL_V4.md)，本章只写产品规则，不重复列定义。实施顺序见 [ROADMAP](./ROADMAP.md)。决策依据见 [ADR-020](./DECISIONS.md#adr-020-真实变美记录与套餐资产分离beautyevent--usagerecord套餐只是可选来源) 至 [ADR-024](./DECISIONS.md#adr-024-行政区与项目分类使用随-app-打包的版本化静态目录)。

### 5B.1 三个互相独立的事实

| 事实 | 用户语言 | v4 是否包含 |
| --- | --- | --- |
| 发生了什么 | 变美记录（一次到店）及其中每一次项目使用 | 是 |
| 买了什么、还剩什么 | 套餐与单次购买（资产） | 是 |
| 以后打算做什么 | 变美计划（BeautyPlan） | **否**，后续独立任务 |

- 三者**不得**合并成一个状态字段，也不得互相推导：套餐里还有余次**不等于**「计划要去做」；心愿单的计划时间**不是**变美计划。
- **真实记录优先**：一条变美记录可以完全不关联任何套餐——单次付费、朋友请客、用了别人的卡、补录的历史、记不清来源，或者只是暂时不想关联。
- 变美记录与套餐资产**可以关联、互相独立**：关联只发生在「这一次使用从哪张卡扣」这一层。

### 5B.2 变美记录与使用记录

- 一条**变美记录**描述一次真实发生的到店：日期、机构、省市、备注。省市不单独填写，取自所选机构（第 5B.9 节）。它**没有**使用人、金额与余次。
- 一条变美记录包含**一条或多条使用记录**。每条使用记录是**一次**项目使用：做了什么项目、谁做的、从哪里扣的次数。同一次到店里的几条使用记录可以各有不同的项目、使用人、来源与撤销状态。
- 撤销只发生在单条使用记录上，撤销后保留、标注「已撤销」，不提供单条删除入口（沿用第 7.2 节）。
- 日期是业务日期，允许补录；修改变美记录的日期、机构、地点与备注**不改变任何次数**。
- 变美记录可以由用户单独删除：二次确认、说明不可恢复，并显示将一并删除的使用记录数与其中会退回套餐的次数。删除变美记录不影响任何套餐、机构与使用人。
- **修正来源**（规则已冻结，由 BT-0023 实现）：
  - 只有**有效**的使用记录可以修改来源；已撤销的记录不能修改来源，需要时新建一条记录。
  - 可以改为另一个仍有余次的购买项目、「外部来源」或「暂不关联」；「原套餐已删除」的记录也可以重新关联到一个有效的套餐或单次购买。
  - 修改在一个事务内完成。关联到新的项目时，保存前再次确认它属于同一档案、仍然存在、仍有余次；使用日期晚于其有效期时沿用第 7.2 节的二次确认；任何一步不满足都不保存。
  - 原来的套餐项目自动退回这一次（余次是算出来的，不需要手工加回）。改为「外部来源」或「暂不关联」时释放次数，已有的历史名称不变。
  - 修改来源不改变这条记录的使用人、日期、机构与撤销状态，也不改动任何套餐。
  - **只改从哪里扣，不改做了什么**：新的购买项目必须是**同一个项目**——目录项目要求是目录中的同一项；自定义项目要求分类相同、名称在统一的规范化处理（忽略大小写、首尾空格、多余空格与全角空格差异）后完全相同。不按名称相近、别名或模糊规则匹配，目录项目与自定义项目不会互相关联。
  - 界面只列出同一项目、仍有余次的购买项目，保存时再独立校验一次；没有这样的项目时只能改为「外部来源」或「暂不关联」。
  - 重新关联后只更新这条记录显示的套餐名称与套餐项目名称，项目分类与项目名称保持不变。
  - 记错了项目**不是**修正来源：已撤销的记录仍不能修改；有效记录能否「修改实际项目」由 BT-0023 另行设计，不能借修正来源绕过。

### 5B.3 「记录一次变美」流程

未来的核心录入流程，按顺序：

1. **选择项目**：一次可选多个，从项目目录选择或自定义（第 5B.10 节）。
2. **事件信息**：日期（默认今天）、机构（可搜索选择或当场新增，沿用第 5A.2 节）、备注。省市跟随所选机构，不单独选择（第 5B.9 节）。
3. **每项使用人**：默认「自己」，可逐项修改（第 5B.4 节）。
4. **每项来源**，四选一：
   - **已有套餐**：从同一档案下仍有余次的套餐项目中选择；保存时在事务内再校验一次余次。套餐已过期时仍可选择，日期晚于有效期时沿用第 7.2 节的二次确认。
   - **本次单独购买**：同时记下这一次的花费，生成一条「单次」购买（第 5B.8 节）。
   - **外部来源**：不属于自己的资产，例如朋友请客、用了别人的卡、活动体验。
   - **暂不关联**：不关联任何来源，以后也可以不关联。
5. **保存**：变美记录与全部使用记录在一个事务内写入，任一条失败整体回滚，不留下半条记录。

- 「新建套餐并使用」是**一个合并事务**：在流程中当场新建套餐（含项目与金额分配）并从中扣本次使用，失败时套餐与变美记录都不写入。
- 重复点击保存不得产生重复记录（沿用 PRD-RED-005、PRD-RED-006 的要求）。
- 界面只使用上面的产品语言，不出现来源的技术取值。
- v4 上线前，现有「快速核销」流程保持不变。

### 5B.4 使用人与购买人

- 同一档案下可以记录多个人。每个档案固定有一个「自己」，不能归档、不能删除，v4 范围内不能改名。
- **购买人**记在购买记录上，**使用人**记在每条使用记录上，两者都必填、默认「自己」。变美记录本身不带人。
- 用户可以添加其他人（只有一个名称），可以改名与归档；已归档的人在历史中照常显示，在新建记录时不再出现。**被任何记录用过的人不能删除**，只能归档。
- 同一档案内人名不得重复，判重规则与机构相同（大小写、首尾空格、多余空格与全角空格不能绕过）。
- **不收集**手机号、身份证号、生日、性别、关系或任何健康信息。
- 历史记录展示当时的名称快照：给某人改名后，旧记录仍显示旧名称。
- 这不是多档案：没有档案切换，也不会为每个人分出一套独立数据（第 5 章、ADR-015 仍有效的部分）。

### 5B.5 快照

- 购买记录保存当时的购买人名称、机构名称与城市（城市取自所选机构）。
- 变美记录保存当时的机构名称与省市：创建时从所选机构复制省、市的代码与名称。
- 使用记录保存当时的使用人名称、项目分类与项目名称，以及来源为套餐或单次购买时的套餐名称与套餐项目名称。
- 快照写入后**永不回写**：机构、人、套餐、项目或目录改名，机构改地点或被归档，都不改变已有记录的展示。唯一例外是用户主动把一条使用记录重新关联到另一个同一项目的购买项目时，它的套餐名称与套餐项目名称改为新来源的名称，项目分类与项目名称不变（第 5B.2 节）。
- 套餐项目的名称**不是**历史快照：它是套餐项目当前的用户可见名称，可以在安全编辑规则内修改；历史上「当时叫什么」以使用记录的快照为准。

### 5B.6 金额分配

- 套餐中每个项目保存**分配到它的总金额**（整数分），单次金额不再保存（[ADR-023](./DECISIONS.md#adr-023-allocated_amount_minor-是套餐项目金额的唯一事实)）。
- 赠送项目可以分配 0 元。
- 编辑时允许部分分配，界面显示「已分配 / 待分配」；分配合计超过总价时不能保存；新建套餐与原本已平衡的套餐，**最终保存时合计必须等于套餐总价**。
- 单次均价只作展示，除不尽时显示「约」，不写回。
- 迁移前已存在、分配合计与总价不一致的套餐原样保留，并标注「金额分配与总价不一致」，同时显示差额。这类套餐：
  - 在项目本身（数量与各自标识）、各项目购买次数、各项目分配金额与套餐总价都不变的前提下，只修改下列内容时可以保留原差额直接保存：套餐名称、购买日期、有效期、机构、购买人、套餐备注、项目名称、项目分类、项目备注；修改项目名称、分类或备注不改变已有使用记录显示的名称；
  - 修改总价、项目购买次数、项目分配金额，或新增、删除项目时，保存前必须补平；
  - App **不会自动修改**任何金额；
  - 这条区分由保存逻辑自己判断，不依赖界面是否拦截。
- 套餐表单改为两步：第一步填套餐信息与总价，第二步添加项目并分配金额（BT-0019C）。

### 5B.7 删除套餐保留真实历史

- 删除套餐仍是二次确认后的永久删除，没有回收站与恢复入口，项目一并删除，机构与人不受影响。
- **相关的变美记录与使用记录全部保留**：使用记录改为「原套餐已删除」，不再占用任何余次，仍展示当时的套餐名称与项目名称快照。
- 确认框显示将删除的项目数，以及**会保留、但不再关联这个套餐**的使用记录数，并说明删除后不可恢复。
- 删除后该套餐不再出现在任何资产列表与资产统计中；相关使用记录仍出现在变美历史与次数类统计中。

### 5B.8 单次购买

- 「本次单独购买」同时生成一条**单次**购买记录（恰好一个项目、购买次数 1、金额等于本次花费、无有效期）并从中扣掉本次使用。
- 用完后不再计入待使用次数与临期提醒。
- 单次购买带「单次」标签，默认**不出现**在「可用套餐」中，但在「全部购买」与相关变美记录中始终可见。
- 若其唯一的使用记录被撤销，这一次重新计入待使用次数，可以在「全部购买」中找到并再次使用。

### 5B.9 结构化地点

- 地点为**省、市两级**，从随 App 打包的行政区目录中选择，不含区县，**不联网**（[ADR-024](./DECISIONS.md#adr-024-行政区与项目分类使用随-app-打包的版本化静态目录)）。
- **结构化地点保存在机构上**：新增或编辑机构（含在套餐、变美记录流程中当场新增）时选择省市，机构同时保存省、市的代码与城市名称。
- 目录中找不到时可选「其他地区 / 暂未收录」并填写文字：省也找不到时不保存任何代码；省已选、市找不到时只保存省的代码与名称，城市文字必填。地点可以不填。
- 变美记录创建时从所选机构复制省、市的代码与名称作为快照；没有选机构时地点为空。之后机构改名、改地点或归档，都不改变已有变美记录的地点。
- 套餐只关联机构，不另存地点代码；套餐的城市文字取自所选机构。
- 迁移时，旧机构与旧核销的城市文字只通过显式对照表映射（如「深圳」「深圳市」）补上代码，城市文字原样保留；对不上的不补代码，不猜测省份。
- 备份包含机构的地点代码与名称；恢复时校验代码与名称是否成对完整。

### 5B.10 项目两级目录

- 项目分为一级分类与二级项目，来自随 App 打包的项目目录；现有七个分类保留为一级分类。
- 找不到时可以自定义项目名称；自定义项目**不会**被自动归并到目录项目，也不会与其他自定义项目自动合并。
- 目录改名只影响以后的显示；已停用的项目在历史中照常显示。
- 项目目录**不是百科**，两者不一一对应；目录只用于记录与归类，**不构成医疗建议，也不声称覆盖全部项目**。
- 迁移时，旧项目名称只有在与目录名称或别名**完全一致且唯一**时才归入目录项目，否则成为自定义项目。

### 5B.11 视图与首页

- 记录 Tab 将来包含三个视图：**项目视图**、**套餐视图**、**变美历史**（页面结构见 [INFORMATION_ARCHITECTURE](./INFORMATION_ARCHITECTURE.md) 第 6 节，均为规划中）。
- **套餐视图**以购买记录为单位展示资产与余次；套餐详情展示当前资产与引用它的使用历史。
- **项目视图**按目录项目**在展示层**汇总余次与使用次数；数据层**从不合并**同名项目或同名套餐，每个套餐项目仍是独立资产，使用时必须落到具体的一个。自定义项目逐条单独显示。
- **变美历史**以变美记录为单位按日期倒序；变美记录详情展示其下全部使用记录（含已撤销）。
- 未来首页展示最近的变美记录与「记录一次变美」快捷入口。临期提醒仍然是**资产提醒**（第 8.4 节口径不变），套餐余次**不是计划**，首页不得据此提示「该去做了」。

### 5B.12 数据升级与备份

- 升级到 schema v4 在一个事务内完成，每条旧核销成为一条变美记录加一条使用记录，购买人与使用人记为「自己」；任何一步校验不过则整体回滚，数据保持升级前的样子。
- 备份格式升级到 v2。新版本 App 可以恢复 v1 与 v2 备份；旧版本 App 读到 v2 备份时提示「这个备份来自更新版本，当前 App 暂时无法恢复。」。不提供导出旧格式。
- 恢复 v1 备份时先在内存中转换为 v2 并完整校验，之后才进入第 15.2.6 节的覆盖恢复流程；原文件不被修改。
- 静态目录不进入备份，备份只携带代码与名称快照。

### 5B.13 不在本章范围

最终 Tab 名称（「记录」是否改名为「变美」见第 20.1 节 Q-15）、变美计划（BeautyPlan）的字段及其与心愿单的关系、完整项目目录与完整行政区数据、云同步、登录、会员、照片、AI 推荐、诊断、社区、机构合作与账单 Tab。

## 6 套餐和购买记录

### 6.1 购买记录（Purchase）字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| id | 是 | UUID |
| ownerAccountId | 是 | 数据所有者 |
| packageName | 是 | 套餐名称 |
| purchaseDate | 是 | 购买日期，YYYY-MM-DD |
| institutionId | 否 | 关联的机构（见第 5A 章） |
| institutionNameSnapshot | 否 | 录入当时的机构名称快照 |
| citySnapshot | 否 | 录入当时的城市快照 |
| totalAmountMinor | 是 | 套餐总金额，整数分 |
| currency | 是 | 币种，第一版默认且仅支持 CNY |
| expiresOn | 否 | 有效期，为空表示未知或长期有效 |
| notes | 否 | 备注 |
| createdAt / updatedAt | 是 | UTC ISO 时间戳 |

一个购买记录包含**一个或多个**套餐项目。

### 6.2 套餐项目（PurchaseItem）字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| id | 是 | UUID |
| purchaseId | 是 | 所属购买记录 |
| catalogEntryId | 否 | 关联的百科标准条目；为空表示自定义项目 |
| displayName | 是 | 套餐项目当前的用户可见名称，可以在安全编辑规则内修改；不是历史快照 |
| category | 是 | 项目分类 |
| unitAmountMinor | 是 | 分摊单价，整数分。必填，允许为 0，**0 表示赠送项目**。**v4 目标**：由分配总额 `allocatedAmountMinor` 取代，见第 5B.6 节 |
| quantity | 是 | 购买次数，正整数 |
| notes | 否 | 备注 |

**派生字段**（不落库、不可编辑）：

- `redeemedCount` = 该项目下 `status = active` 的核销记录数
- `remaining` = `quantity - redeemedCount`

### 6.3 项目分类

第一版分类沿用原有业务口径：光电类、注射类、化学焕肤、中胚层微针、清洁、手术类、其他。

- 分类用于筛选与统计，不承载医学含义。
- 项目名称可从百科标准条目选择、按别名搜索，或在找不到时自定义输入。
- 自定义项目不进入官方百科，仅属于该用户的记录。

### 6.4 业务规则

- **金额按分保存整数，页面以元展示**，业务逻辑中不得出现浮点累计（[ADR-006](./DECISIONS.md#adr-006-金额使用整数分)）。
- `quantity` 必须为大于等于 1 的整数。
- `unitAmountMinor` **必填**，不得留空；允许填 0，**0 表示赠送项目**，不得为负数。
- 项目分摊总额 = `unitAmountMinor × quantity`，为派生值，不落库。
- 套餐总价**允许**与各项目"分摊单价 × 次数"之和不同，以支持折扣、赠送与无法精确分摊的组合套餐。
- 二者差额超过 1 元时**提示用户确认，但不禁止保存**。该提示是业务层规则，不在存储层阻断保存。
- 编辑 `quantity` 时**不得小于该项目的有效核销次数**；该限制由表单与保存事务**两层**共同保证，页面停留期间产生的新核销同样会被拦下（[ADR-018](./DECISIONS.md#adr-018-编辑套餐时项目能否删除以是否存在核销历史为界)）。
- **编辑套餐时，项目能否删除以是否存在核销历史为界**（[ADR-018](./DECISIONS.md#adr-018-编辑套餐时项目能否删除以是否存在核销历史为界)）：
  - 完全没有核销记录的项目可以删除，删除前必须二次确认并说明不可恢复。
  - **只要该项目存在任何核销记录就不允许删除，已撤销的记录同样算历史**；此时向用户说明原因，并告知仍可修改该项目的名称、分类、次数、金额与备注。
  - 一个套餐至少保留一个项目，最后一个项目不能删除。
  - 编辑既有项目时保留其原有标识，不得以"全部删除后重新插入"的方式实现，否则会连带失去其核销历史。
- **编辑套餐的机构或城市，不改写既有核销记录中的机构与城市快照**：核销快照记录的是那一次实际完成的地点（见第 5A 章、PRD-INST-005）。
- **删除套餐是不可恢复的永久删除**（[ADR-016](./DECISIONS.md#adr-016-套餐永久删除核销记录使用作废机制)）。**v4 目标**：自 schema v4 起，删除套餐不再删除真实的变美记录，相关使用记录改为「原套餐已删除」并保留快照（[ADR-021](./DECISIONS.md#adr-021-删除套餐不再删除真实历史使用记录保留历史快照)，第 5B.7 节）；以下为当前（schema v3）行为：
  - 必须二次确认，确认前明确显示将受影响的**项目数量与核销记录数量**。
  - 确认框必须明确告知**删除后不可恢复**。
  - 用户确认后物理删除该套餐，其**项目与核销记录一并级联删除**。
  - 删除后相关数据**不再进入任何历史统计**。
  - **不提供回收站，不提供恢复入口。**
  - **机构不随套餐删除**，仍由机构归档规则管理；个人档案同样不受影响。
- `expiresOn` 可为空；有值时不得早于 `purchaseDate`。
- 机构名称与城市保留历史快照，避免机构改名导致旧记录失真。

## 7 核销记录

> **v4 目标（已批准，尚未实现）**：schema v4 起，核销记录（`redemption_records`）退役，逐行迁移为「变美记录 + 使用记录」（[ADR-020](./DECISIONS.md#adr-020-真实变美记录与套餐资产分离beautyevent--usagerecord套餐只是可选来源)，第 5B 章）。本章规则在 v4 上线前继续有效；其中「剩余次数 = 购买次数 − 有效使用次数」「单条纠错只能作废」「过期不阻止使用」三条在 v4 中原样保留，只是计数对象换成使用记录。

### 7.1 核销（Redemption）字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| id | 是 | UUID |
| purchaseItemId | 是 | 对应套餐项目 |
| redeemedOn | 是 | 核销日期，YYYY-MM-DD |
| institutionId | 否 | 实际完成机构（见第 5A 章） |
| institutionNameSnapshot | 否 | 机构名称快照 |
| citySnapshot | 否 | 城市快照 |
| status | 是 | `active`（有效）或 `void`（已作废） |
| notes | 否 | 备注 |
| createdAt | 是 | UTC ISO 时间戳 |
| voidedAt | 否 | 作废时间 |
| voidReason | 否 | 作废原因 |

### 7.2 业务规则

- **剩余次数 = 购买次数 − 有效核销数量**，只统计 `status = active` 的记录。
- 剩余次数为 0 时**禁止继续核销**，入口需置为不可用并说明原因。
- **重复点击不得产生重复核销**：确认后立即禁用按钮并显示进行中状态；客户端为每次核销生成唯一请求标识；同一标识重试不得产生第二条记录。
- 用户可以**作废**误操作的核销记录，作废后对应剩余次数自动恢复。
- 作废记录**保留**，不做物理删除，保留 `voidedAt` 与 `voidReason` 审计字段（[ADR-016](./DECISIONS.md#adr-016-套餐永久删除核销记录使用作废机制)）。
- **不提供删除单条核销记录的入口**：单次核销的唯一纠错路径是作废。这与"删除套餐为永久删除"并不矛盾——两者是不同粒度、不同误操作概率的操作。
- 套餐被永久删除时，其下的核销记录随之级联删除，这是整条记录被清除，而不是单条核销的纠错路径。
- 修改核销的日期、机构、城市与备注**不影响次数**。
- 核销默认继承套餐的机构与城市，日期默认今天，**均允许修改**；机构可改为另一个已有机构，也可当场新增（见第 5A 章）。
- 允许补录历史日期；当核销日期早于购买日期时提示确认，但允许保存（覆盖转卡、补录等情况）。
- **套餐过期不阻止核销，也不清零余次**（[ADR-017](./DECISIONS.md#adr-017-套餐过期后仍允许核销但保存前必须明确提醒)）：
  - 当**核销日期晚于套餐有效期**时，保存前提示确认，确认框中同时显示套餐有效期与本次核销日期；确认后照常保存，该次核销计为已使用，剩余次数减 1。
  - 判断依据是核销日期与有效期的比较，**不是**「今天是否已过有效期」；补录一条发生在有效期之内的核销不提示。
  - 提示文案只陈述日期事实，不把「已过期」描述为医疗风险，不给出治疗或效果判断。
  - 用户选择返回检查时不保存，已填写内容保留。
  - 有效期为空的套餐不参与该判断（见 E-10）。
- 不允许通过直接编辑剩余次数来修复数据；纠错路径只有"新增核销"与"作废核销"。

### 7.3 术语表达

用户界面使用"撤销核销"等产品语言，不向用户暴露 `void`、`active` 等技术术语。

## 8 首页

首页优先回答"我还有什么没用完""我接下来要做什么"，**第一阶段不追求复杂图表**。

### 8.1 首屏内容

- 待核销项目数量。
- 剩余总次数。
- 临期套餐提示与数量。
- 临期提醒区（最多 3 个套餐，常驻"查看全部"入口，见第 8.4 节）。
- 快速新增购买记录入口。
- 快速核销入口。

### 8.2 后续内容

- 最近一次核销（项目、日期、机构）。
- 近期记录（最近三条核销）。
- 临期与已过期套餐列表入口。
- 长期未核销项目提示（仅陈述事实，不做频率评价）。
- 消费摘要与统计入口。
- 收藏或心愿单的轻量回访入口。

### 8.3 状态要求

- **空状态**：引导用户添加第一条购买记录，并说明录入后可以管理剩余次数，不只显示"暂无数据"。
- **加载状态**：本地已有缓存时优先展示缓存，不得等待所有远程请求完成才渲染。
- **错误状态**：远程失败时展示可重试入口，并标明数据可能不是最新。

### 8.4 临期与过期提醒

本节定义**应用内**的临期与过期提醒。系统推送通知、本地通知权限与后台任务不在本节范围内，仍属第 12 章的 R4 内容。

#### 8.4.1 提醒口径

- 提醒窗口为**未来 30 个自然日**，第一版**固定**，用户不可配置。可配置阈值与推送提醒的默认值仍见第 20.1 节 Q-12。
- 只提醒**仍有剩余次数**的套餐。套餐剩余次数 = 各项目 `max(0, quantity − 有效核销数)` 之和；已撤销的核销不占用次数。
- `expires_on` 为空的套餐**不进入提醒**（E-10）。剩余次数为 0 的套餐不进入提醒，即使已临期或已过期。
- 提醒状态、剩余次数与剩余天数**均为派生值，不落库**：它们随当天日期变化，存下来就会立刻过时。
- 判断基准是**设备当前本地日历日期**。

#### 8.4.2 状态定义

以基准日期 today 计：

| 状态 | 条件 | 文案 |
| --- | --- | --- |
| 已过期 | `expires_on < today` 且剩余次数 > 0 | "已过期1天" / "已过期N天" |
| 今天到期 | `expires_on = today` 且剩余次数 > 0 | "今天到期" |
| 即将到期 | `today < expires_on <= today + 30 天` 且剩余次数 > 0 | "明天到期" / "N天后到期" |
| 不提醒 | `expires_on > today + 30 天`、`expires_on` 为空，或剩余次数 = 0 | 不出现在提醒中 |

- 到期当天**不算已过期**，显示"今天到期"。
- 距今 30 天纳入提醒，31 天不纳入。
- 提醒文案必须**同时显示明确日期**，例如"今天到期 · 2026-09-18""12天后到期 · 2026-09-30""已过期8天 · 2026-09-10"，不得只显示相对时间。
- 提醒只陈述日期事实，不把"已过期"描述为医疗风险，不出现"该做第二次了""建议复购"等指令性或推销性表述（PRD-NFR-002）。
- **已过期的套餐仍然可以核销**，剩余次数不因过期归零，核销入口不禁用（[ADR-017](./DECISIONS.md#adr-017-套餐过期后仍允许核销但保存前必须明确提醒)、PRD-RED-014）。核销日期晚于有效期时沿用第 7.2 节的二次确认，本节不新增第二套规则。

#### 8.4.3 首页提醒区

- 位置在快捷操作与"最近记录"之间，标题"临期提醒"。
- 最多展示 3 个套餐，顺序为已过期在前、其后按到期日期由近及远。
- 右上角常驻次要文字入口"查看全部"，进入完整提醒页；条数不足 3 条时该入口同样存在且位置不变。
- 每张卡片展示套餐名称、机构名称（为空时显示"未填写机构"）、到期状态与有效期日期、套餐剩余总次数；点击进入该套餐详情。
- 没有需要提醒的套餐时只显示一行轻量说明（例如"未来 30 天没有需要提醒的套餐"），不占用整块空状态卡片。
- 临期查询未完成不得阻塞整张首页，该区块单独显示轻量加载提示。

#### 8.4.4 完整提醒页

- 标题"临期提醒"，位于首页 Tab 的导航栈内，底部 Tab 栏保持显示。
- 分两个区块："已过期"在前，"30天内到期"（含今天到期）在后。
- 排序：已过期按有效期倒序（最近过期在前）；30天内按有效期升序（最早到期在前）；相同日期按购买日期倒序，再按记录标识升序保证顺序稳定。
- 整行可点击进入所属套餐详情。本页**只读**，不提供核销、编辑有效期或删除的入口。
- 空状态提示"暂无临期套餐"并说明未来 30 天没有需要提醒且仍有剩余次数的套餐；查询失败时提示"没能读取临期提醒"并提供重试，后台刷新失败保留已有内容并标明可能不是最新。

## 9 记录模块

### 9.1 购买记录列表

- 默认以套餐为组织单位，按购买日期倒序。
- 展示套餐名称、购买日期、机构、总价、项目数量与总剩余次数、有效期状态。
- 筛选：全部、待核销、已用完、临期、已过期。
- 搜索：套餐名、项目名、机构名。
- 维度筛选：项目分类、机构、城市。
- 筛选条件可一键清除，从详情返回列表时尽量保留用户已选条件。

### 9.2 项目余次视图

以套餐项目为单位的扁平视图，展示项目名称、所属套餐、已核销次数、剩余次数与有效期，支持按剩余次数排序，便于用户直接找到"还没做完的"。

### 9.3 购买记录详情

- 套餐基础信息、总价、有效期。
- 项目列表，每项展示购买次数、已核销次数、剩余次数与分摊单价。
- 按时间倒序的核销记录。
- 操作：编辑套餐、对有余次的项目快速核销、查看与撤销单条核销、删除套餐。
- 项目名称若关联百科条目，可跳转到对应条目。

### 9.4 新增和编辑购买记录

- 套餐字段：套餐名称、购买日期、机构、城市、总价、有效期、备注。
- 机构字段为可搜索的选择器，列出已录入机构，并支持当场新增（见第 5A 章）。
- 项目字段：项目名称、分类、分摊单价、购买次数、备注；**至少包含一个项目**。
- 保存前校验必填项、数字格式与日期关系（见第 6.4、7.2 节）。
- 编辑态展示每个项目的已核销次数，并阻止将次数改到小于该值。
- 编辑态可以新增项目；删除项目的限制见第 6.4 节与 E-17。
- 保存失败或网络异常时**不得静默丢失用户已填写内容**。

### 9.5 核销

- 入口：首页快捷核销、项目余次视图、购买记录详情。
- 字段：对应项目、核销日期、机构、城市、备注。
- 默认值与防重复要求见第 7.2 节。
- 保存成功后刷新该项目剩余次数、套餐详情与首页统计。

### 9.6 核销历史

核销历史是一个**独立页面**，集中展示当前档案下所有套餐、所有项目的核销记录，入口为记录列表页的次要入口（不与"添加套餐"同级）。

- 数据范围：当前档案下的全部核销记录，**含已用完与已过期套餐下的记录**，也**含已撤销的记录**。已被永久删除的套餐，其核销记录已随套餐一并消失，不再出现（见第 6.4 节、ADR-016）。
- **状态筛选为"全部 / 有效 / 已撤销"三项，默认"全部"**："全部"同时包含有效与已撤销，"有效"只含有效，"已撤销"只含已撤销。切换筛选只刷新历史列表，不影响记录列表自身的筛选条件。
- 排序：按核销日期倒序；同一天按录入时间倒序，保证顺序稳定。
- **按核销日期所属的自然月份分组展示**（例如"2026年9月"）。分组只是展示方式，不改变任何记录的业务日期。
- 每条记录展示项目名称、所属套餐名称、核销日期、状态、**核销当时的机构与城市快照**，以及备注。机构快照为空时显示"未填写机构"，城市为空时整段省略。
- 已撤销的记录**保留并可见**，明确标注"已撤销"，可展示撤销时间；撤销原因为空时不显示虚假占位。已撤销不计入有效核销次数，也不影响剩余次数。
- 点击一条记录进入其所属套餐的详情页。历史页面**只用于查看**：撤销仍在套餐详情中完成（见第 7.2 节），页面不提供编辑或删除单条核销的入口。
- 顶部展示当前筛选下的记录条数，数量来自真实查询结果。
- 后续增强（不作为当前上线阻塞条件）：按项目分类、项目与机构筛选，以及总核销次数、平均间隔天数与最近一次日期的统计。
- **时间间隔只作事实展示**：不得仅凭固定天数将用户标记为"正常""过快"或"应该复购"，不得据此推动消费。是否适合再次进行必须提示咨询具备资质的医生。

### 9.7 状态要求

- 空状态：区分"从未录入"与"当前筛选无结果"，后者提供清除筛选入口。
- 加载状态：列表首次加载展示骨架，翻页展示局部加载。
- 错误状态：展示失败原因与重试按钮，已缓存数据继续可见。

## 10 百科模块

### 10.1 分类体系

百科的分类分两层，**两层不是同一件事，不得混用**：

#### 10.1.1 首版浏览分类（已实现）

首版数据模型、首页筛选与搜索**只使用**以下四个分类。分类值在代码中使用稳定英文代码，中文名称只用于显示。

| 代码 | 显示名称 | 收录范围 |
| --- | --- | --- |
| `basics` | 基础认知 | 如何看待医美项目的效果、风险与个体差异 |
| `lightAndEnergy` | 光电项目 | 依靠光、射频、超声等能量作用于皮肤的项目 |
| `injectables` | 注射项目 | 填充与注射类项目 |
| `careAndSafety` | 护理与安全 | 恢复期护理、术前沟通与术后观察 |

- 首页提供「全部」+ 上述四类，默认「全部」，**单轴筛选**。
- 一篇文章只属于一个分类。
- 不实现「内容类型 × 分类」的双轴筛选。

#### 10.1.2 长期内容类型体系（尚未实现）

以下五类是内容规模扩大之后的扩展方向，**首版未落地**，不出现在数据模型与界面中，后续需要单独任务评估是否引入、以及如何与首版四分类共存：

1. 医美项目
2. 仪器
3. 注射材料
4. 常见成分
5. 原理科普

### 10.2 百科条目字段

首版条目采用**自由章节结构**，而不是固定正文栏位：不同类型的文章（项目介绍、护理清单、基础认知）需要的小标题并不相同，强行套同一套模板会产生空栏位或凑数内容。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| id | 是 | 稳定标识，全库唯一 |
| slug | 是 | 可读标识，全库唯一，用于路由 |
| title | 是 | 标题 |
| summary | 是 | 一句话摘要 |
| category | 是 | 第 10.1.1 节四个分类之一 |
| tags | 是 | 标签，列表卡片最多展示 3 个 |
| aliases | 是 | 搜索别名 |
| sections | 是 | 结构化正文章节，至少一个；每节含小标题与段落 |
| limitations | 是 | 「需要知道的限制」 |
| seekHelp | 是 | 「什么时候应及时联系专业人员」 |
| sources | 是 | 资料来源，每条含机构、标题、URL 与来源类型 |
| reviewedOn | 是 | 内容与来源的复核日期，YYYY-MM-DD |
| reviewStatus | 是 | 审核状态，见第 10.2.1 节 |

#### 10.2.1 审核状态（reviewStatus）

| 取值 | 含义 | 详情页文案 |
| --- | --- | --- |
| `draft` | 内容草稿，来源或正文尚未完成核验 | 内容正在整理，尚未完成资料核验 |
| `sourceChecked` | 资料来源已逐条核验，但尚未经过专业医学人员复核 | 资料来源已核验，尚待专业人员复核 |
| `expertReviewed` | 已由明确的专业医学责任人复核 | 资料来源已核验，并经专业人员复核 |

- **首版所有文章最多只能标记到 `sourceChecked`**：专业审核责任人尚未确定（第 20.1 节 Q-04），本轮不得出现 `expertReviewed`，完整性校验会直接拦下。
- `reviewedOn` 表示**本次内容与来源的复核日期**，不代表医生或专业医学人员的背书。
- 详情页必须展示审核状态，但不得使用「权威认证」「医生已审核」等容易误导的表述。
- 不得虚构审核人、医生、机构或审核资质。
- Q-04 不因引入 `reviewStatus` 而关闭，仍为未决事项。

#### 10.2.2 资料来源要求

- 来源限于国家级监管机构、公立医疗体系、医学专业学会、同行评议的系统综述与指南共识、WHO 等权威主体。
- **治疗类文章原则上至少 2 个独立权威来源**；基础认知类至少 1 个。
- 每条来源必须包含机构或作者、标题、URL 与来源类型，URL 必须实际核验可访问。
- 不引用商业医美机构的营销文章，不引用社交平台、论坛与短视频内容。
- 正文由编辑自行概括，不大段复制来源原文。

### 10.3 功能

首版（已实现）：

- 浏览文章列表，按第 10.1.1 节四个分类筛选。
- 搜索：范围为标题、摘要、标签与别名；去首尾空格、折叠连续空白、英文大小写不敏感、中文直接包含匹配；多词之间为「与」的关系，每个词命中任一字段即可；搜索与分类筛选同时生效；结果保持编辑顺序，不做相关性评分，不保存搜索历史。
- 文章详情：分类标签、标题、摘要、中立提示条、正文章节、需要知道的限制、什么时候应及时联系专业人员、资料来源、审核状态与复核日期。
- 资料来源在系统浏览器中打开，不内嵌浏览器。
- 正文随 App 本地打包，**无网络时也能阅读**。
- 文章详情提供**收藏与取消收藏**（见第 11.1 节），以及**加入心愿单**（见第 11.5 节）。两者互相独立：收藏不是加入心愿单的前提，加入心愿单也不会自动收藏。

后续版本：

- 相关内容跳转。
- 从记录模块的项目名称跳转到对应条目。
- 独立搜索页与从新增套餐表单选择项目后回填。

### 10.4 内容边界

- 官方百科第一阶段**聚焦非手术轻医美**；用户仍可通过自定义项目记录其他历史项目。
- 科普内容**不构成诊断或治疗建议**，条目内必须有明确的免责说明。
- 事实信息、一般性说明与个体化建议必须在表达上区分。
- 禁止出现保证性效果描述、绝对安全表述、诱导性焦虑文案与未经审核的个体治疗建议。
- 涉及风险、禁忌与并发症时使用准确、中性措辞。
- 使用「可能」「通常」「部分人」等限定词；区分常见短期反应、可能出现的风险与需要及时求助的异常，不把常见写成必然，也不把罕见写成不可能。
- 禁用「绝对安全」「永久有效」「零风险」「一次见效」「无恢复期」等绝对化表述。
- 不出现具体医院、医生与商业品牌，不出现设备型号、药物剂量、能量参数与操作教程，不提供价格信息与项目排名。
- 不判断某个人是否适合某个项目，不给个体治疗方案与疗程安排；是否适合必须提示咨询具备资质的医生。
- 不允许机构付费影响百科事实、搜索结果或风险提示。
- 条目下架后，用户历史收藏保留必要说明，但不得继续展示失效医疗信息。

## 11 收藏与心愿单

### 11.1 收藏

收藏是用户在百科里记下的「以后还想再看一遍」的文章。它与心愿单同属「以后还想了解 / 还想做」，因此放在**心愿单 Tab** 的第二个视图里，不另开一级入口。

收藏**不是医疗推荐**：系统不因为用户收藏了什么而推断适合做什么，也不据此推送项目、机构或促销（[ADR-009](./DECISIONS.md#adr-009-ai-定位为记录与科普助手不是医生)）。

#### 11.1.1 首版字段（已实现）

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| profileId | 是 | 数据所有者，查询与写入一律按档案隔离 |
| articleSlug | 是 | 被收藏文章的稳定标识 |
| createdAt | 是 | 收藏时间，UTC ISO 时间戳 |

- `(profileId, articleSlug)` 唯一：同一档案对同一篇文章最多只有一条收藏。
- **数据库只保存文章标识**：标题、摘要、分类与正文仍然只存在于随 App 打包的本地内容中，展示时按标识回本地内容取当前文本。把文本复制进数据库只会在内容更新后留下两份互相矛盾的版本。
- 因此收藏也**不依赖网络**，离线可收藏、可取消、可浏览收藏列表。
- 文章更新后标识不变；万一某个标识在本地内容中已不存在，该条收藏被安全跳过，不显示占位的假文章，也不因此崩溃或清空列表。

#### 11.1.2 首版功能（已实现）

- 在文章详情收藏与取消收藏，状态同时用图标与文字表达（「收藏文章」/「已收藏」）。
- 心愿单 Tab 的「收藏文章」视图展示收藏列表，按收藏时间倒序，顶部显示「共 N 篇收藏」。
- 点击收藏卡片进入该文章原文，返回时回到收藏列表。
- 收藏落本地数据库，App 重启后仍在。

#### 11.1.3 后续版本

- 收藏列表按内容类型或浏览分类筛选。
- 条目下架后在收藏中保留并标注（E-14）。
- 收藏排序、文件夹、收藏备注与收藏内搜索。
- 收藏随账号云端同步（R2 起）。

### 11.2 心愿单（WishlistItem）

心愿单是**用户自己记下的关注对象**：想了解、以后也许想做的项目。它不是待办清单，不是计划表，也不是消费目标。

#### 11.2.1 首版字段（已实现）

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| id | 是 | UUID |
| profileId | 是 | 数据所有者，查询一律按档案隔离 |
| name | 是 | 心愿名称，保存前去除首尾空格。**唯一的必填字段** |
| category | 否 | 项目分类，取值沿用第 6.3 节套餐项目的同一套分类，不另起一套同义分类 |
| institutionId | 否 | 意向机构，**只能引用已有机构**，见第 11.3 节 |
| plannedOn | 否 | 计划时间，YYYY-MM-DD。只是用户自己的打算，**不产生任何提醒** |
| budgetMinor | 否 | 心理预算，整数分，允许为 0，不得为负数（ADR-006） |
| notes | 否 | 备注 |
| createdAt / updatedAt | 是 | UTC ISO 时间戳 |

- 只有名称必填。用户在百科里看到一个项目想记下来时往往还没有机构、预算与时间，强制填写只会让人放弃记录。
- 首版**不含**完成状态、优先级、提醒时间与关联百科条目，见第 11.4 节。
- 心愿**不保存机构名称快照**，列表展示机构**当前**的名称。这与购买记录、核销记录刻意相反：后两者记录的是"那一次实际发生时的事实"，必须保留快照（第 5A.2 节、PRD-INST-005）；心愿记录的是"现在还想去哪"，机构改名后应当显示新名称。

#### 11.2.2 首版功能（已实现）

- 心愿单 Tab 分「心愿项目」与「收藏文章」两个视图，默认停在「心愿项目」；「收藏文章」是第 11.1 节的收藏列表，不是另一个 Tab。
- 心愿单列表：按最近更新倒序，展示名称、分类、机构、计划时间、心理预算与备注摘要；选填项为空时整段省略。
- 新增心愿、编辑心愿。
- **永久删除**一条心愿：二次确认后物理删除，无回收站、无恢复入口。删除只影响这一条心愿，不波及机构、套餐与核销记录。

### 11.3 规则

- 意向机构**只能从已有机构中选择，不能当场新增**。这与新增套餐、新增核销刻意不同（第 5A.2 节）：那两处是"事情已经发生在某家机构"，用户必须能把当时那家写下来；心愿只是"以后也许想去"，为一个尚未发生的打算凭空创建机构主数据，会让机构管理里堆满从未产生任何记录的空机构。
- 关联的机构被归档时，**既有关联不被清空**，心愿仍指向原机构；归档状态必须在界面上用文字说明，不只靠颜色（PRD-NFR-005）。
- 计划时间即使已经过去，也**只陈述日期事实**，不出现"已错过""该去了"等评价或催促（PRD-NFR-002）。
- 心愿单**不得**基于用户行为推送购买引导，不出现推荐、猜你喜欢、按记录推断、倒计时与促销式强调。
- 系统**不自动生成消费记录**，不自动记账。

### 11.4 后续版本

以下内容**首版不做**，不属于当前范围，需在对应阶段单独评估后落地（对应 R3 / Phase 4）：

- 心愿状态（想了解、考虑中、计划进行、已完成、已放弃）与优先级。
- 心愿标记为"已完成"时选择**创建或关联一条购买记录**；创建时带入已有信息（项目名称、机构、预算作为金额初值），**用户确认金额、机构与套餐项目后才保存**。
- 心愿与百科条目的**长期关联**（首版只有一次性预填，见第 11.5 节）。
- 收藏列表的筛选、排序与下架标注（第 11.1.3 节）。

这些能力进入产品后，第 11.3 节"不自动记账""不推送购买引导"的约束继续适用。

### 11.5 从百科加入心愿单（已实现）

文章详情提供一个独立的「加入心愿单」入口，它做的事情只有一件：**打开新增心愿表单并预填几个初始值**。

- 名称预填为文章标题。
- 分类**只在能唯一映射时**预填，映射规则见下表；映射不唯一时留空，由用户自己选。
- 机构、计划时间、心理预算与备注一律留空。
- 所有预填值都是**初始值**，用户可以随意修改；未做任何修改就返回，不弹放弃确认。
- 保存仍走与手动新增**完全相同**的流程与校验，存下来的心愿与手动新增的没有任何区别。

| 文章浏览分类 | 预填的心愿分类 |
| --- | --- |
| `lightAndEnergy` 光电项目 | 光电类 |
| `injectables` 注射项目 | 注射类 |
| `basics` 基础认知 | 不预填 |
| `careAndSafety` 护理与安全 | 不预填 |

映射只按分类代码进行，**不猜测文章标题里的字词**。

**保存后的心愿不与文章保持长期绑定**：`wishlist_items` 不保存文章标识，心愿页不显示"来自某篇文章"，文章页也不显示"你已经加过心愿"。同一篇文章可以多次加入心愿单，系统不阻止，也不合并。保留长期绑定属于第 11.4 节的后续能力。

进入表单时若文章标识已经失效，给一句中性说明「没有找到对应的百科内容，你仍可以手动填写心愿。」并照常打开空白表单，不显示技术细节。

「加入心愿单」与收藏互相独立：既不要求先收藏，也不会顺带收藏。文案只陈述"加入心愿单"这个动作，不写成"推荐项目"，也不构成任何医疗建议。

## 12 提醒

本章定义**主动推送式**提醒，实施阶段见第 19 章（对应 R4 版本，[ROADMAP Phase 5](./ROADMAP.md)）。**应用内**的临期与过期提醒（首页提醒区与完整提醒页）不依赖通知权限，已在第 8.4 节单独定义并先行落地。

| 提醒类型 | 说明 | 实施阶段 |
| --- | --- | --- |
| 套餐临期提醒 | 有效期临近且仍有剩余次数时提醒。应用内展示见第 8.4 节（已落地）；此处指系统通知推送 | R4 |
| 剩余次数提醒 | 长期未核销且有余次的项目提醒 | R4 |
| 用户计划时间提醒 | 心愿单计划时间到达前提醒 | R4 |
| 一般护理周期信息提示 | 仅作为**用户可选择的参考模板**，需标注为一般性信息 | R4 |
| 用户主动创建的预约提醒 | 用户自行设置日期与内容 | R4 |

### 12.1 规则

- 所有提醒允许关闭或调整频率。
- 临期阈值由用户设置，默认值在内测后确定，**不写死医学周期**。第一版的应用内提醒窗口固定为未来 30 个自然日且不提供设置项（第 8.4 节）；可配置阈值属于本章范围，见第 20.1 节 Q-12。
- 提醒文案**不得写成医疗治疗指令**，不得出现"该做第二次了""建议复购"等指令性或推销性表述。
- 一般护理周期只能作为用户主动选择的模板，不得自动生成带治疗指令性质的通知。

## 13 统计

### 13.1 统计口径

> **v4 目标（已批准，尚未实现）**：下表按 v3 的分摊单价书写。v4 起基于分配金额的口径改用 `allocated_amount_minor`（单次按 `allocated ÷ quantity` 派生，见第 5B.6 节），核销改为来源为套餐或单次购买的有效使用记录；统计本身仍属 R4。

| 统计项 | 口径 |
| --- | --- |
| 按购买日期统计支出 | 按 `purchaseDate` 落入所选区间的 `Purchase.totalAmountMinor` 求和 |
| 按核销日期统计实际消耗金额 | 按 `redeemedOn` 落入所选区间的有效核销，累计其 `PurchaseItem.unitAmountMinor` |
| 已核销金额 | 全部有效核销对应的分摊金额之和 |
| 待核销金额 | 各项目 `unitAmountMinor × remaining` 之和 |
| 按项目分类 | 以 `PurchaseItem.category` 聚合 |
| 按项目 | 以 `PurchaseItem.displayName` 聚合（关联百科条目时按标准名称归并） |
| 按机构 | 以 Institution 实体聚合（见第 5A 章） |
| 按月份 / 年份 | 依据所选统计口径对应的日期字段 |

### 13.2 规则

- 两种口径（按购买 / 按核销）必须在界面上明确标注，不得混用后给出单一"总消费"。
- 当项目分摊总额与套餐总价不一致时，基于分摊的统计需标注为**估算值**。
- 所有金额由整数分格式化展示。
- 支持年度与月份筛选。

### 13.3 空数据表现

- 无任何记录：展示引导录入的空状态，不展示 0 值图表。
- 所选区间无数据：明确提示"该区间没有记录"，并保留切换区间的入口，不回退到全量数据。
- 某一维度无数据：该维度区块隐藏或标注为无数据，不显示空图表框。

## 14 AI 辅助

AI **不作为第一阶段核心闭环的阻塞功能**，在 R4 版本经单独评审后接入。所有调用必须经过服务端，客户端不得保存模型密钥。

### 14.1 AI 允许

- 总结用户已有记录。
- 提醒待核销项目与临期项目。
- 解释有来源的一般性公开知识。
- 生成用户面诊时可以询问医生的问题。

### 14.2 AI 禁止

- 自称医生、皮肤科医生或"私人皮肤科医生"。
- 诊断疾病或判断当前皮肤状态。
- 判断用户一定适合或不适合某个项目。
- 给出确定的治疗方案，或直接规定下次项目与时间。
- 承诺治疗效果，或表示可替代医生面诊。
- 以促销为目的推荐机构或项目。

上述边界为合规底线，见 [ADR-009](./DECISIONS.md#adr-009-ai-定位为记录与科普助手不是医生) 与 [PROJECT_BRIEF 第 7 节](./PROJECT_BRIEF.md#7-产品边界ai-能力红线)。所有提示词、输出文案与 UI 说明都须体现"记录助手 + 科普助手"的定位，并具备越界拦截。

## 15 我的与数据权利

### 15.1 功能清单

- 账号信息。
- 提醒设置。
- 数据备份导出与从备份恢复（已实现，见第 15.2 节）。
- 数据导入（是否在 V1 开放见第 20.1 节 Q-13）；从**本 App 的备份文件**恢复数据见第 15.2.6 节，与第 15.3 节的通用导入不是同一件事。
- 账号注销。
- 删除个人数据。
- 隐私政策。
- 用户协议。
- 内容免责声明。
- 关于 App。
- 意见反馈。
- 清除本地缓存。

### 15.2 数据备份导出与恢复

用户的记录只存在这一台设备上。备份的作用是让用户**自己**持有一份可以带走的副本：换手机、误删 App、送修之前，先导出一次；换到新设备或误删之后，用这份文件把数据放回去。

- 用户可导出个人结构化数据，至少提供 JSON；Excel 作为后续增强能力。
- 用户可以从一个本 App 导出的 JSON 备份文件恢复数据。
- 入口在「我的」的「数据管理」区块，页面见 [INFORMATION_ARCHITECTURE 第 3.5.4 节](./INFORMATION_ARCHITECTURE.md)。

#### 15.2.1 本版范围

- 导出与恢复都是**本地文件**操作：不上传服务器，不做云同步，不做自动备份与定时备份。
- 恢复只接受**本 App 导出的 JSON 备份**，不支持压缩包、加密备份与其他 App 的导出文件。
- 恢复是**整体覆盖**，不是合并；不提供选择性恢复（详见第 15.2.6 节）。
- 通用的 Excel / 第三方数据导入仍见第 15.3 节，是另一件事，不在本版范围内。

#### 15.2.2 备份文件格式与版本

- 备份是**一个 JSON 文件**，不是压缩包，不分片。
- 文件包含三个互不相同的版本概念，任何一个都不得用来替代另一个：

| 字段 | 含义 | 何时变化 |
| --- | --- | --- |
| `format` | 固定标识，用于区分「这是本 App 的备份」而不是别的文件 | 不变 |
| `formatVersion` | **备份文档格式**的版本 | 备份文件的字段结构发生变化时 +1 |
| `databaseSchemaVersion` | 导出当时的**本地数据库 schema 版本** | 由 migration 决定，与备份格式无关 |

- App 版本号**不写入**备份：它既不决定格式，也不决定 schema，写进去只会让人误以为必须用同一个 App 版本才能恢复。
- 导出时还写入 `exportedAt`（UTC ISO 时间戳）。它是备份内容中**唯一**会随时间变化的字段：同一份数据连续导出两次，除 `exportedAt` 外应逐字节一致。
- 读取备份时必须校验 `format` 与 `formatVersion`；不认识的版本要明确拒绝，不得"尽力解析"。
- `databaseSchemaVersion` 必须是整数，且**不得高于**当前 App 支持的最新数据库版本；高于则拒绝恢复。
- **任何情况下都不得因为文件里写着什么而修改本机数据库的版本**：备份不是 migration（[ADR-019](./DECISIONS.md#adr-019-从备份恢复采用整体覆盖--单事务备份文件一律当作不可信输入)）。

#### 15.2.3 导出范围

导出当前档案下的全部结构化记录，**含**以下容易被漏掉的部分：

| 内容 | 说明 |
| --- | --- |
| 档案 | 当前档案本身；不导出其他档案的任何数据 |
| 机构 | **含已归档的机构** |
| 套餐与套餐项目 | 全部字段，含机构名称与城市快照 |
| 核销记录 | **含已撤销的记录**，保留撤销时间与撤销原因 |
| 心愿 | 全部字段 |
| 百科收藏 | **只有文章标识**，不含标题、摘要与正文 |

**不导出**：其他档案的数据、SQLite 内部表、PRAGMA、索引定义、migration SQL、派生的剩余次数、派生统计、格式化后的人民币字符串、界面展示文案、百科正文与资料来源、临时的搜索与筛选状态、调试日志、SQL 错误、文件系统绝对路径。

派生值不进备份的理由是一致性：剩余次数由购买次数与有效核销数算出（第 7.2 节），把它也存一份，一旦两者对不上就无法判断哪个是真的。

导出内容需说明**生成时间**（`exportedAt`）；套餐、项目、机构与核销记录以完整数组给出，条数可直接由数组长度得到。本版**不再另写一份计数摘要**——同一个事实在文件里出现两遍，只会在两者对不上时多一个需要判断真伪的地方。

#### 15.2.4 金额与文本

- 金额一律按**整数分**导出，与库内存储一致（[ADR-006](./DECISIONS.md#adr-006-金额使用整数分)）。备份中不出现「¥199.99」这类展示字符串，也不出现以元为单位的浮点数。
- 中文、全角标点与 emoji 必须原样往返，不得转义成不可读形式或丢字。
- 值为空的字段导出为 JSON `null`，不得改写成空字符串或 0——「没填备注」和「备注是空字符串」在恢复时是两件事。

#### 15.2.5 隐私与安全

- 备份包含用户的消费记录与机构信息，属于**个人敏感数据**。页面上必须中性提示用户保存到自己信任的位置，不制造焦虑，也不暗示不备份会有后果。
- 导出**不上传到任何服务器**，不经过网络，不接入 analytics。文件去向完全由用户在系统分享面板中决定。
- 临时文件只写入 App 的缓存或临时目录，分享结束后（无论成功、失败还是用户取消）都必须清理；不写入源码目录，不写入数据库目录。
- 失败提示只给一句中文业务说明，不显示 SQL、表名、绝对路径与堆栈；原始错误只在开发期日志中记录。
- 备份内容本身不得打印到日志。
- 导出是**只读操作**：不得修改、删除或"顺手整理"任何一行数据。
- 恢复时只读取**用户主动选中的那一个文件**：不扫描目录、不按文件名猜测、不读取上一次的路径，也不读写任何其他文件。系统为读取而生成的缓存副本在读完后立即删除。
- 绝对文件路径既不显示给用户，也不写进日志：路径里通常带着设备名、账号名与网盘容器标识。
- 导出与恢复都**不为此申请任何新的系统权限**。

#### 15.2.6 从备份恢复

恢复的语义只有一句话：**让这台设备回到那份备份被导出的那一刻**。

##### 15.2.6.1 覆盖，不是合并

- 恢复**整体覆盖**当前档案：备份里有的写回去，**库里有、备份里没有的会被删除**。
- **不做合并、不做追加、不做选择性恢复**，不提供「只恢复心愿单」这类勾选。合并会产生一个既不是现在、也不是备份时刻的第三种状态，用户无从判断哪一份是真的。
- 业务记录的标识、创建与更新时间、空值、整数分金额、核销的有效与已撤销状态、撤销时间与原因、机构与城市快照**原样写回**，不重新生成标识，不刷新更新时间，不重算并保存任何派生值（剩余次数仍然是算出来的）。
- 恢复完成后**无法在 App 内撤销**。因此页面上要建议用户在恢复之前先导出一次当前数据。

##### 15.2.6.2 备份文件是不可信输入

- 文件扩展名与系统给出的类型只是**提示**，不作为信任依据；无论如何都要做完整的结构校验。
- **不执行备份文件中的任何 SQL、表名或列名指令**；文件里多出来的字段会让校验失败，而不是被当作指令执行。
- 文件体积上限为 **10 MiB**，在解析 JSON 与进入任何事务之前就挡下。系统给出的体积不可信时，按读入内容的真实字节数再量一次。

##### 15.2.6.3 恢复前的校验

以下检查**全部在写入之前**完成，任何一条不过都不进入恢复：

- 文件是合法 JSON，顶层字段齐全且类型正确，七类数据均为数组。
- `format` 完全匹配，`formatVersion` 在支持范围内，`databaseSchemaVersion` 为整数且不高于当前版本。
- 各类记录的标识不重复；文档中只有一个档案。
- 全部归属关系合法，不存在跨档案的数据。
- 套餐项目指向存在的套餐，核销指向存在的套餐项目，心愿的意向机构存在或为空，购买与核销引用的机构存在。
- 日期、时间戳、金额、次数与状态满足既有业务约束：金额为非负整数分，购买次数至少为 1，日期为合法的 `YYYY-MM-DD`，有效期不早于购买日期，核销状态只能是有效或已撤销，且已撤销必须有撤销时间、有效必须没有。
- 机构的重名判定与收藏的唯一性不会在恢复后产生冲突。

##### 15.2.6.4 恢复摘要与二次确认

- 校验通过后**先展示摘要，不写任何数据**：备份生成时间、备份格式版本，以及套餐、套餐项目、核销记录、机构、心愿与收藏文章的数量。
- 用户在摘要下点击危险按钮「恢复这份备份」，随后出现最终确认框：
  - 标题「用这份备份覆盖当前数据？」
  - 说明「当前 App 中的套餐、核销、机构、心愿和收藏将被替换为备份中的内容。恢复完成后无法在 App 内撤销。」
  - 两个选项：「返回检查」与「确认恢复」。
- 文案必须明确说出"覆盖"与"无法撤销"，**不得**使用「同步」「导入一些数据」「继续」这类模糊说法。
- **取消是零改动的正常操作**：用户关掉文件选择器，或在确认框里选「返回检查」，都不报错、不改动任何一行数据。

##### 15.2.6.5 全成或全不成

- 全部写入在**一个事务**内完成：先按依赖关系删除当前档案的数据，再按依赖顺序写回，写完后在事务内自查行数与引用完整性。
- 任何一步失败都整体回滚，数据库**逐行**回到恢复之前，不会出现半旧半新或被清空的状态；此时不显示成功，用户可以重试。
- 失败提示只给一句中文业务说明，不显示原始异常、SQL、表名、绝对路径与堆栈。用户可见文案至少区分这几种情况：

| 情况 | 文案 |
| --- | --- |
| 不是合法 JSON 或不是本 App 的备份 | 这个文件不是有效的备份文件。 |
| 来自更新的格式或数据库版本 | 这个备份来自更新版本，当前 App 暂时无法恢复。 |
| 内容不完整或关联对不上 | 备份内容不完整或存在关联错误。 |
| 超过体积上限 | 备份文件过大，无法恢复。 |
| 写入失败已回滚 | 恢复没有完成，你的数据没有被改动。 |

- 恢复成功后给一条克制的提示（例如「数据已从备份恢复」），随后回到首页；首页、记录、机构管理、心愿单与收藏重新读取数据库，不需要用户重启 App。
- 导出与恢复**互斥**：一个在进行时不能发起另一个；连续快速点击「确认恢复」只执行一次恢复。恢复进行中不提供取消按钮——中途取消正是最容易留下半套数据的做法。

### 15.3 数据导入

- 任何导入都必须**先预览、再确认执行**，并输出成功、跳过与失败的数量及原因。
- 去重**不得只依赖"套餐名 + 日期 + 机构"三元组**——同一天同一机构可能购买两个同名套餐。必须优先使用源记录 ID、导入批次 ID 与明确的用户确认机制。
- 导入具有唯一批次标识，同一批次重复提交不产生重复数据。
- 导入失败不得删除原始数据。

### 15.4 账号注销与数据删除

- 注销前说明影响并二次确认。
- 注销完成后按政策删除或匿名化相关数据。
- 不得以隐藏入口或额外营销步骤阻碍用户注销。
- 隐私政策、用户协议与内容免责声明在未登录状态下也可访问。

## 16 异常与边界场景

| 编号 | 场景 | 期望行为 |
| --- | --- | --- |
| E-01 | 无网络 | 展示离线标识；已缓存数据可查看；写操作暂存并提示"待同步"，不谎报成功 |
| E-02 | 请求超时 | 明确提示失败与可重试；不保留"进行中"死状态；用户能判断操作是否成功 |
| E-03 | 重复提交 | 同一操作使用唯一请求标识；重试不产生第二条记录；按钮在进行中禁用 |
| E-04 | 多设备修改冲突 | 使用版本号或 `updatedAt` 检测；冲突时提示刷新或保留用户输入，**不静默覆盖** |
| E-05 | 套餐余次为 0 | 核销入口不可用并说明原因；不得允许负数余次 |
| E-06 | 编辑数量小于已核销数 | 阻止保存，提示当前有效核销次数与最小可填值；保存时再校验一次，页面停留期间新产生的核销同样被拦下 |
| E-07 | App 保存过程中退出 | 重新进入时恢复未提交的表单内容，或明确告知未保存；不静默清空 |
| E-08 | 删除套餐 | 二次确认，显示将受影响的项目数与核销记录数，并明确告知不可恢复；确认后物理删除，项目与核销记录级联删除；无回收站与恢复入口；机构不随之删除 |
| E-09 | 作废核销 | 剩余次数恢复；记录保留并标记作废时间与原因；可在历史中查看 |
| E-10 | 有效期为空 | 视为未知或长期有效；不参与临期与过期筛选；不显示"已过期" |
| E-11 | 金额分摊不一致 | 差额超过 1 元时提示确认；允许保存；相关统计标注为估算值 |
| E-12 | 自定义项目与标准项目重名 | 允许保存；提示存在同名标准条目并提供关联入口；统计按是否关联条目分别归并，不自动合并 |
| E-13 | 账号登录后本地数据迁移 | 首次登录明确询问是否导入；可预览数量；批次唯一；重复提交不产生重复数据；成功后保留结果摘要；失败不删除原始本地数据 |
| E-14 | 百科条目下架 | 收藏与关联记录保留，标注内容已下架，不再展示失效医疗信息 |
| E-15 | 核销日期早于购买日期 | 提示确认，允许保存（支持补录与转卡） |
| E-16 | 核销日期晚于套餐有效期 | 提示确认并同时显示套餐有效期与本次核销日期；确认后允许保存，剩余次数照常减 1；过期本身不清零余次，也不禁用核销入口（[ADR-017](./DECISIONS.md#adr-017-套餐过期后仍允许核销但保存前必须明确提醒)） |
| E-17 | 编辑套餐时删除项目 | 无任何核销记录才可删除，删除前二次确认并说明不可恢复；存在核销记录（含已撤销）时阻止删除并说明原因，同时告知仍可修改该项目；最后一个项目不可删除（[ADR-018](./DECISIONS.md#adr-018-编辑套餐时项目能否删除以是否存在核销历史为界)） |
| E-18 | 编辑过程中套餐或项目被改动 | 套餐已被删除时提示找不到该套餐，不新建替代记录；项目在此期间产生新核销导致次数或删除不再合法时，整次保存被拒绝并提示刷新重试，已填内容保留，不部分写入 |

## 17 非功能需求

### 17.1 数据安全

- 认证凭证存入系统安全存储，不写入普通本地存储。
- 用户数据接口必须校验账号归属，不得仅依赖客户端传入的 accountId。
- 服务端密钥不得出现在移动端代码、`EXPO_PUBLIC` 环境变量或 Git 仓库中。
- 传输使用 HTTPS。

### 17.2 隐私最小化

- V1 不申请相机与相册权限，不收集照片。
- 只收集实现核心功能所必需的数据。
- 实际收集的个人信息必须与隐私政策声明一致。
- 用户记录属于用户个人数据，不因汇总进入平台就自动成为可交易的数据资产。

### 17.3 性能

- 常规冷启动应让用户在可接受时间内看到可交互骨架或缓存数据。
- 本地已有数据时，首页不等待所有远程请求完成才显示。
- 记录列表支持数百个套餐与数千条核销记录顺畅滚动。
- 搜索输入需防抖，避免每个字符触发远程请求。
- 具体毫秒指标在建立真实测试环境后确定，**不在缺少基线时虚构**。

### 17.4 可访问性

- 表单输入与标签关联。
- 关键操作提供屏幕阅读器标签。
- 不只依赖颜色表达状态。
- 文本与背景保持足够对比度。
- 支持系统字体缩放，核心内容不被截断。

### 17.5 可恢复性

- 换设备登录后可恢复云端数据。
- 长表单在切换页面或网络失败时不丢失已填内容。
- 写操作失败可重试，重试幂等。

### 17.6 日志脱敏

- 日志不得记录完整手机号、访问令牌、备注全文或完整消费明细。
- 分析事件不记录项目备注、完整机构输入、手机号、令牌等敏感内容。

### 17.7 兼容性

- iOS 与 Android 共用主要业务代码。
- iOS 为首个开发与体验验证平台。
- Web 仅作为开发期辅助预览，不作为 V1 正式发布平台（[ADR-003](./DECISIONS.md#adr-003-移动端优先web-只作为辅助预览)）。
- 最低系统版本在正式构建前结合 Expo SDK 与目标用户设备确定。

### 17.8 简体中文优先

所有用户可见文字默认使用简体中文；术语使用用户语言，不暴露技术字段名。

### 17.9 业务日期的选择方式（已实现，BT-0019A）

- 购买日期、有效期、核销日期与心愿计划时间在 iOS 与 Android 上通过**系统日期选择器**选择，不再手工输入 `YYYY-MM-DD`；新增与编辑使用同一个日期字段。
- 保存的业务值仍是 `YYYY-MM-DD`，各字段的必填规则、默认值与校验（第 6.4、7.2、11.2 节）**均未改变**；数据库仍为 schema v3。
- 选填日期（有效期、计划时间）可以「清除日期」；必填日期不能清除。在选择器中取消不改变已填内容。
- 有效期的选择器以购买日期为最早可选日期，这只是交互提示，「有效期不能早于购买日期」仍由保存校验把关；改购买日期不会自动改有效期。核销日期不限制可选范围，早于购买日期或晚于有效期时仍按第 7.2 节二次确认。
- Web 仅作开发预览（[ADR-003](./DECISIONS.md#adr-003-移动端优先web-只作为辅助预览)），日期字段退回按 `YYYY-MM-DD` 填写的文本框，沿用同一套校验。

## 附录 B 产品验证指标

公开测试阶段重点验证是否形成真实记录与长期价值，不以下载量单独判断。

- 首条记录完成率、核销激活率、四周记录留存。
- 百科周活跃、收藏或心愿使用率。
- 数据准确性反馈（用户报告余次错误、重复核销或数据丢失的数量）。
- 提醒有效性（收到提醒后查看对应套餐或心愿的比例）。

正式目标值在首批 20 至 50 名种子用户形成基线后确定，**当前不虚构数值**。
